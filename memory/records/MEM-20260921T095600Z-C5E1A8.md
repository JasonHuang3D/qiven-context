# GitHub CI runs are explicit-dispatch-only; observation is preconditioned on creation

Incident (2026-09-21, jason-extended-cognition session): after pushing the
RCA-0 branch and opening PR #9 on qiven-foundation, the session performed
three bounded observations "for CI" — but no run had ever been created. The
root cause was a contract gap, not tool failure: `session-ci-handoff-contract`
described what to do after dispatch without stating that a dispatch must
happen at all, and the session defaulted to the industry assumption that a
push auto-triggers CI. Qiven workflows are workflow_dispatch-only, so the
push correctly triggered nothing.

Owner direction (binding):

1. No push, PR, schedule or other automation may trigger a Qiven workflow.
   A run exists only through deliberate dispatch (Operator `ci start`,
   `gh workflow run`, Actions UI).
2. The three-observation / 60-second budget applies only after run creation
   is CONFIRMED. Exhausted budget → stop observing, record identity and last
   state, proceed.
3. Public repo + free-tier runners is the deployment shape, but remote CI is
   warranted only for repositories with an explicit cross-platform contract
   that need OS environments beyond the local validation device. A
   platform-first repo validated on its local device (e.g. Windows-first
   qiven-runtime on JasonPC) does not need remote CI for that acceptance;
   full coverage is a deliberate later escalation.

Contract: `collaboration/session-ci-handoff-contract.md`, sections "Remote-CI
necessity criterion", "Explicit dispatch requirement", and the amended
"Chat-side asynchronous CI rule".
