# Checkpoints are turn-interruption insurance - event-driven, never time-budgeted

Owner-clarified semantics (2026-09-22):

1. **Purpose**: a session checkpoint bounds the loss when a turn ends
   unexpectedly - network drop, accidental stop-click, harness or
   provider failure. It exists so the next turn (or the next session's
   cold boot) resumes from recorded state instead of conversation
   memory.
2. **Cadence is event-driven, never time-driven**: refresh at material
   boundaries (candidate staged, gate run, publication, blocker,
   next-action change) because those are the points where
   interruption would lose decisions - not because any clock says so.
   No turn-duration budget exists in Qiven; the formerly observed
   ~26-minute ChatGPT tool-turn boundary was a ChatGPT platform
   limitation (superseded record MEM-20260915T135800Z-6B0D8A) and does
   not apply to ZCode+GLM or any other harness.
3. **No coupling to batch planning**: planning batches, completing
   development and accepting checkpoints are separate concerns.
   Project recovery runs through canonical state plus cold boot;
   the checkpoint is only the turn-scoped continuity layer on top
   (constitution section 5 unchanged: nothing that must survive the
   session may exist ONLY in a checkpoint).

Wording rule for contracts and workflow docs: describe checkpoints as
interruption insurance with event-driven refresh points; never imply a
turn time limit, a time-based budget, or a development-milestone
obligation.
