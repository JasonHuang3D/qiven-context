# Bounded process custody: the survival law for anything that spawns

The v19 aftermath incident (2026-09-23) proved that "the child survives
the caller" implemented WITHOUT a bound, and cleaned up only by agent
discipline (`exec stop`), is an operational hazard: MSBuild node-reuse
descendants and abandoned runs accumulated invisibly until the machine
needed a restart. The law, now implemented as exec v2 (watchdog + Job
Object):

- **A spawned tree's lifetime is bounded by the OS kernel, not by any
  agent's memory.** Windows: the run's Job Object carries
  `KILL_ON_JOB_CLOSE`; the watchdog custodian JOINS its own job and
  holds the only handle — custodian death (any cause) kills the tree
  instantly. A hard lease (`--max-lifetime`) bounds the run even with a
  living custodian and no caller.
- **Completion reaps.** The primary's exit terminates surviving tree
  members after a short output grace — deliberate background survivors
  are the leak class, not a feature (no-daemon law).
- **Nothing escapes the job**: children never spawn with
  `CREATE_BREAKAWAY_FROM_JOB`; task children are created suspended,
  assigned, then resumed (zero-race custody).
- **Sweep insurance rides every operator invocation**: expired runs are
  terminated, stale records finalized — dead-man coverage without a
  daemon.
- Tool children that can fan out worker nodes additionally run with
  `MSBUILDDISABLENODEREUSE=1` (the leak amplifier, defense in depth).

Any NEW tool that spawns processes must consume this custody layer (or
the operator's exec) rather than reinventing looser spawn semantics.
The design contract is qiven-devkit `docs/design/exec-custody.md`;
the Python law including the Windows spawn scar tissue is
qiven-devkit `docs/engineering/python-standard.md`.
