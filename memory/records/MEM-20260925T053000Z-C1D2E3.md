# Self-review loops need an explicit materiality line or they never converge

The owner's 3-consecutive-pass rule (any revision voids the count) is
the strong guarantee that the approving rounds certify the FINAL state.
But a fresh-context reviewer essentially always finds SOMETHING at P3:
five rounds produced five different minor-finding sets with almost no
overlap. Without a materiality line the loop is infinite.

The line that converged (v29, disclosed to the owner for veto): a
finding resets the count only when it changes the admission decision -
wrong identity numbers (generations, SHAs the decision binds to),
honesty gaps in the delivery report's disclosed-open rows, or
correctness defects in the delivered code. Latent nits that cannot fire
under the current graph (unconsumed variables, unreachable collisions,
typed-fail paths) and precision drift in aggregate accounting become
recorded observations with triggers (obligations), riding later batches.

Second measurement: the loop materially improved the artifact before it
approved it - two genuine defects were found and fixed (a
generation-label factual error in the admission-bound report; a real
authoritative-mode gap: the resolver consumed a dirty control working
tree branded with the admitted HEAD - fixed as typed ControlTreeDirty +
self-test R22, lock-update flow exempt). The fixes cost three count
resets; the approved state is strictly better than what a single
reviewer pass would have admitted.

Third: each round must be briefed fresh with no knowledge of prior
rounds' findings (independence is the value; fix verification is the
orchestrator's job, not the next round's).

Owner adjudication 2026-09-26 (v31 turn 3, verbatim 全批): the
materiality line as drawn is ACCEPTED — it is now standing law for
self-review approval loops, not a pending disclosure.
