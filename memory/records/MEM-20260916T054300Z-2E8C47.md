# Host transport must bound peer-controlled waiting and preserve session identity through transport uncertainty

Bounding connection count does not bound execution liveness. A local peer that can cause `ConnectNamedPipe`, `ReadFile`, or `WriteFile` to wait indefinitely can consume a Host transport slot or caller thread indefinitely even when handle and memory counts remain fixed. Peer-controlled waits therefore require explicit deadlines and cancellable I/O at the transport owner.

The accepted Windows transport uses overlapped pipe handles. Server accept/read/write and client read/write apply an explicit peer-facing deadline and cancel the exact outstanding operation with `CancelIoEx` on timeout. Stack-owned `OVERLAPPED` storage is not released until Windows reports completion of the cancellation/completion path. The deadline is therefore a bound on peer-controlled waiting, not a claim of hard real-time progress under an arbitrarily failed kernel or NPFS implementation.

Once Host has published a `BrokerSessionId`, transport uncertainty must not erase that authority identity. A cleanly disconnected or timed-out connection enters `Retiring` and preserves the exact session until the future dispatcher performs authority-side disconnect/reconciliation and explicitly retires the slot. If native disconnect/reuse safety cannot be proven, the slot enters `Poisoned`: the published session remains readable for cleanup, but I/O, accept, and retirement are refused until server replacement.

Acceptance harnesses require an independent higher-level liveness fuse. The Windows local-pipe CTest has a 20-second timeout so a future deadlock becomes explicit failure evidence rather than an indefinitely running CI job. Test orchestration may use bounded retry for an expected transient `ERROR_PIPE_BUSY` race when the test itself has just started an accept thread; production client behavior remains immediate `busy` with no hidden queue or retry.
