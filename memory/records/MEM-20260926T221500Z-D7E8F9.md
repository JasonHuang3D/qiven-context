# Gate coverage is the tested boundary; suites outside it are untested in practice

1. **The configured publication gate defines what is actually tested.**
   The repo/local suite split (repo group = "fast, every commit"; tools
   group = validator mutation tests) meant `qiven gate` (context-local)
   never executed `validator-unit` — so `validator_fixture.py` missing
   `runtime/invocation-policy.yaml` (required by `validate_context.py`
   since the 2026-09-24 boundary) produced ZERO failing publication
   receipts for two days. Every recorded PASS was honest; the coverage
   boundary was the defect.
2. **A bare full-runner run caught it immediately** — the wider entry
   (tools/test_all.py, all groups) failed on first contact. When two
   validation entries exist, the publication receipt must ride the
   WIDER one unless the cost is real; the fast/full split's rationale
   (the ~5-minute gate era) is obsolete at ~15s full / ~1.6s repo.
   Resolution: default_gate flipped to context-tools (all groups in the
   publication gate); merge-proof synced.
3. **Canonical invocation matters for more than formality**: the
   configured tasks pin `.venv/Scripts/python.exe`; a bare
   `python tools/test_all.py` picks the system interpreter, which lacks
   the repo's dependencies (ModuleNotFoundError: yaml) — and piping the
   gate through a text filter masks its exit code (MEM-D5E6F7 class,
   nearly re-committed the same day). Publication receipts come from
   `qiven gate`; dev-loop runs use the venv interpreter directly and are
   never piped.
