# Polling supervision is the anti-pattern; the harness already sells the fix

The 2026-09-23 long-command architecture routed every long-class
command through `qiven exec start` + `qiven exec status` polling (and
the user-level layer mandated foreground `sleep && tail`). Both are the
same defect: supervision via intermediate LLM round-trips. Each
round-trip re-sends the ENTIRE live session context, so supervising one
long command costs O(polls x context-size) — in a long session that
dominates the cost of the work itself. The original motivations were
real but already solved elsewhere: unbounded remote-CI observation is
prohibited by the explicit-dispatch-only CI law, and shell-death
killing commands is solved by custody, not polling.

The platform already carries the correct primitives:

1. `run_in_background: true` — one call returns an output-file path
   immediately; the harness re-invokes the model ONCE on completion.
   Tasks are tracked and killable (TaskStop). Zero polls.
2. Oversized foreground output auto-persists to a file with a ~2KB
   preview + path — the "output too long" insurance needs no custom
   hook (and none is possible: PostToolUse cannot rewrite tool
   results).

Lesson, generalized: BEFORE building a custom mechanism to compensate
for a suspected platform limitation, PROBE what the platform natively
does. The exec detour was designed against an assumed limitation
("background is unreliable", "output floods context") that probing
would have disproven in minutes. Design the mechanism survey into the
ADR step: capabilities-first, custom-tooling second, and only for the
classes the platform cannot bound (custody across session death is
genuinely outside the harness's promise — exec v2 keeps exactly that
slice).
