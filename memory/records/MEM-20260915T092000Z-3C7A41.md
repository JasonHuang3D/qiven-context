# Use DCR as the accepted bounded substitute for human CMD relay on JasonPC

The reliable baseline workflow remains: jason-brother decides the repository, exact operation, validation scope, and command chain; JasonPC executes it; the observed result returns to Chat. DCR is now accepted as the preferred transport for this bounded execution step because live acceptance proved it can execute the same class of Git/SSH and local validation operations without requiring the project owner to relay CMD text and output manually.

DCR is an execution transport, not an autonomous local engineering authority. It must not independently broaden scope, select a new engineering objective, merge or push without authorization, change Git identity, weaken credentials/security, or continue from an unexpected failure into an open-ended repair loop. The established human CMD path remains the fallback when DCR is unavailable or when the requested capability has not been validated.

For Git/SSH on the accepted JasonPC environment, every DCR-launched process must restore `ProgramData=C:\ProgramData` before Windows OpenSSH is used. Desktop Commander Remote 0.2.50 / its MCP SDK environment boundary omits that variable, and Windows OpenSSH 9.5 exits `255` when it is absent. This root cause was isolated experimentally and is recorded in `MEM-20260915T101200Z-91B4F0` and `evidence/audits/dcr-acceptance-2026-09-15.md`.

Canonical DCR Git/SSH execution also uses explicit, deterministic paths and noninteractive controls: Windows OpenSSH at `C:\Windows\System32\OpenSSH\ssh.exe`, SSH config at `C:\Users\61626\.ssh\config`, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=Never`, SSH `BatchMode=yes`, zero password prompts, and disabled password/keyboard-interactive authentication. Strict host-key checking and the existing Clash ProxyCommand remain intact.

Do not rely on ambient executable discovery when a validated canonical path exists. In particular, use `C:\Env\python\3.14.7\python.exe` rather than bare `py` until the launcher discrepancy is separately resolved. Tool versions are mutable operational state, not permanent architecture; revalidate material drift before release-critical use.

DCR lifecycle may also be self-managed by an authorized Work/local execution task. Acceptance proved that Work can start `npx @wonderwhy-er/desktop-commander@latest remote` in the active `JASONPC\61626` session without owner credentials, a service, scheduled task, persistent elevation, or startup persistence. Lifecycle automation must positively track the exact DCR process tree and stop only that instance; do not kill generic `node.exe`, `cmd.exe`, or PowerShell processes by name.

The execution identity boundary must distinguish the Work/Codex runner, the DCR server process, and DCR-launched children. A successful DCR connection alone is not evidence that child-process environment/network semantics match the owner's foreground CMD; capability is accepted only after the relevant operation is demonstrated with truthful exit behavior.

DCR is valuable primarily because it compresses repetitive human relay turns while preserving the same authority model. This supports long-running Qiven continuity together with qiven-context, which remains the authoritative project cognition source; model-native cross-session memory is not a substitute for canonical retrieval.
