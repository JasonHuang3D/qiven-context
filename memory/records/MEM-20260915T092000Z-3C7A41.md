# Use DCR as a bounded substitute for human CMD validation before considering autonomous local execution

The established reliable validation workflow is: jason-brother prepares remote GitHub work and an exact Windows CMD validation chain; the project owner runs that chain on JasonPC, then returns the observed result. This human copy/paste path remains the fallback authority because it was repeatedly validated in Qiven-v2 and Qiven-v3.

During Qiven-v4, Desktop Commander Remote (DCR) is introduced conservatively. Its first role is only to execute the same already-decided local command chain that would otherwise be handed to the owner. DCR is a transport/executor for a bounded operation, not an autonomous local engineering agent.

For this initial mode:

- jason-brother decides the repository, exact operation, validation scope, and command chain before DCR execution;
- DCR must not independently broaden scope, choose a new validation objective, install or repair tools, alter PATH/system configuration, change Git identity, rewrite credentials, or continue through an unexpected failure;
- a non-zero exit, interactive prompt, device loss, unexpected output, or ambiguous environment condition terminates the DCR attempt and returns control to Chat;
- when the DCR path is unsuitable or fails, fall back to the established human copy/paste CMD workflow rather than improvising a larger local-agent loop;
- the foreground `npx @wonderwhy-er/desktop-commander@latest remote` process is part of the current transport liveness boundary: the project owner keeps it open and can observe calls/results; closing it makes JasonPC unavailable to DCR;
- DCR process environment must not be assumed identical to the owner's foreground CMD environment. The 2026-09-15 baseline observed `py --version` as 3.14.7 in human CMD but 3.9.6 through DCR even though both resolved `C:\Windows\py.exe`. Prefer explicit known executables or repository-owned validated resolvers over ambient launcher assumptions.

JasonPC tool versions are mutable operational state, not permanent architectural invariants. Upgrades are allowed. When a product or release-critical local validation materially depends on the host environment, perform a read-only revalidation and record material drift rather than forbidding updates or silently assuming the old snapshot is current.
