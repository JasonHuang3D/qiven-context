# Coverage-map honesty is mechanical, not narrative

A 104/104-green gate shipped (v35) whose receipt claimed coverage it did
not have. Three successive fresh reviews each found a further layer of
the same defect class, all invisible to the green count:

1. **An invariant credited in the coverage map must have an assertion
   site.** INV-10 (whole-transaction bound) was claimed via a constant
   that no case ever read; INV-15 (deny-without-effect) was bound to the
   Edit matrix, every Bash deny leg and P16/P17 without a single
   before/after effect check there.
2. **A case name must be generated from the same parameterization as
   its payload.** Four governed-Write legs replayed one shared template
   target under four different governed-path names - the names lied.
3. **Allow-asserting legs never bind deny invariants (and vice versa).**
   The coverage map is generated from the bindings; a misbound case
   credits the wrong invariant with real coverage.
4. **The receipt binds EVERY behavior-shaping fixture.** The
   invocation-policy fixture drove host admission and freshness behavior
   while only the catalogue digest was recorded - a swapped policy was
   undetectable by verify-receipt.
5. **The designated consistency check must read the rows, not the
   counters.** verify-receipt accepted a receipt with FAIL rows and
   zeroed `failed`/`skipped` fields because it only compared aggregate
   numbers.

The working rule that converged: review the COVERAGE MAP as a claim
table (invariant -> asserting case -> assertion site -> oracle source),
not the code as prose. Anything in the map without all four cells is a
finding regardless of the green count.
