# Zero-job failing runs mean an invalid workflow file; annotations first; whole-file claims need whole-file validation

Three-layer scar (2026-09-22):

1. **The template carried poison.** The devkit bootstrap-only CI
   template used `matrix.id` in a job-level `if:` — invalid because
   GitHub evaluates job-level conditions before strategy expansion.
   Every adopted repo inherited an invalid CI file silently: under the
   dispatch-only policy nobody dispatched, so nobody saw the UI banner
   until the owner opened the workflow page. Untested capability paths
   in shared templates rot invisibly.
2. **Region-of-interest comparison overclaimed.** The investigation
   byte-compared the trigger blocks of three repos, found them
   equivalent, and concluded "the file is clean" — while the defect sat
   in the jobs section, outside the compared region. A file-equivalence
   claim requires validating the WHOLE file (GitHub's own parser being
   the authority), not the region under suspicion.
3. **`gh run list`/`gh run view` hide workflow-file validation
   errors.** The CLI is not defective; its listing simply does not
   carry them. They surface in the workflow page UI and via the
   check-run annotations API
   (`gh api repos/<owner>/<repo>/check-runs/<id>/annotations`).

Operating rules that follow: a zero-job failing run on any event is a
parse/evaluation failure of the workflow file — query annotations
FIRST, before theorizing about platform anomalies or registrations; a
"platform-side defect" classification requires having read the
platform's own error message; and a dispatch-only CI policy should
include a periodic one-dispatch smoke of the workflow file so template
poison surfaces at adoption time, not at the owner's UI visit.
