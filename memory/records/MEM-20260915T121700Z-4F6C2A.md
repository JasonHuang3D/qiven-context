# Recover controller or DCR interruption by reconciling durable state before replay

An unexpected Chat/controller/tool/DCR interruption does not prove that already-dispatched work stopped or that a mutation failed. Controller lifetime, acknowledgement delivery, DCR relay/server lifetime, local process state, filesystem state, and Git state are separate evidence domains.

The 2026-09-15 follow-up proved that DCR had not been refreshed: the same local-MCP process retained 244 tool-call records from the prior turn, including the last completed file writes, and had no active terminal sessions. The exact reason the Chat turn ended remains unknown; a similar-duration controller execution boundary is a hypothesis, not an accepted fact.

After any such interruption, prove current DCR liveness, inspect recent tool history and active sessions when available, reconcile target filesystem/Git/process state, and resume from the last proven boundary. Replay a mutation only after evidence shows it did not already complete.

Long-running Qiven workflows should therefore tolerate controller disappearance between steps. Non-idempotent actions need atomic semantics, durable operation identity, or exact post-operation reconciliation so a lost acknowledgement cannot cause duplicate mutation.

Human CMD remains fallback when DCR cannot be restored or reconciled promptly.
