# Long-running human-facing tasks must provide truthful liveness and progress feedback

Any Qiven task, command, automation, worker flow, validation runner, installer, compiler step, migration, or other operation that can remain visibly silent long enough for a human operator to reasonably suspect a hang should expose liveness rather than relying on eventual completion output.

The preferred interaction contract is:

- acknowledge start promptly and identify the major work that is running;
- use a stable, readable output layout for human-facing command entry points such as `test.cmd`, `test.sh`, validation runners, and similar orchestration scripts;
- use visually distinct status tags such as `[ RUN]`, `[WAIT]`, `[ OK ]`, and `[FAIL]`, with color when the terminal supports it and a deterministic no-color path for CI/redirected output;
- emit periodic heartbeat/progress feedback while meaningful output is otherwise silent;
- report real milestones as they complete, including elapsed time when useful;
- emit a concise final PASS/FAIL/completion summary;
- keep detailed logs buffered or structured when concurrent or expected-negative-path output would become unreadable, and print detailed logs by default only for actual enclosing-suite failures unless verbose output was explicitly requested;
- never let log cleanliness make the process appear dead.

Progress reporting must remain epistemically honest. Do not invent percentages, ETAs, completed stages, or forward motion that the program cannot actually observe. A heartbeat may say that work is still running and how long it has run; it must not pretend to know more.

Cadence is proportional to expected duration rather than a universal timer. For an interactive local task that normally takes tens of seconds, roughly five seconds of silence is a useful default heartbeat interval. Longer jobs can report less frequently, and naturally chatty jobs do not need redundant heartbeat noise.

Human-facing test runners should prefer explicit controls analogous to `QIVEN_TEST_VERBOSE=1` and `QIVEN_TEST_NO_COLOR=1` when useful, rather than forcing either maximum log volume or ANSI output on every environment. When practical, print the repository/exact HEAD near startup so copied logs retain provenance.

The reason is operational, not cosmetic: prolonged silence, visually noisy expected-failure output, or ambiguous final status can cause a human operator to misdiagnose healthy work as deadlocked or failed, terminate valid processes, rerun work unnecessarily, or lose trust in automation. Human-visible progress and output structure are therefore part of reliability and observability for long-running workflows.
