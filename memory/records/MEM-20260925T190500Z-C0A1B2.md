# The v30 desktop-PoC incident, recorded in full

Owner adjudication (2026-09-26): a disaster-class incident caused by the
session's own overconfidence. Recorded completely, including everything
the session cannot prove about itself.

## Verified timeline (+0800, from harness transcript timestamps)

- 00:58:35 - the session launches `pnpm dev:desktop:test`; build runs;
  the "ZCode Dev" window appears ~01:00 with official onboarding and a
  login screen. No warning has reached the owner.
- ~01:01 - the owner, seeing an unexplained login screen and no
  instruction, completes a real login including SMS verification. The
  popup browser inherited the scratch environment (the isolated trial's
  own design), and the login return errored.
- 01:03:24 - the session's instruction text ("do not log in...") reaches
  the UI - roughly three minutes after the login-demanding window
  appeared, and after the login was already done.
- 01:03:55 - the polling loop starts.
- 01:19 onward - the owner's Chrome is in a broken state: extensions
  not loading, every login failing ("Failed to decrypt token" in
  Chrome's own log; the breadth across all sites is the app-bound
  encryption key invalidation signature). All site login states were
  ultimately lost; the owner re-authenticated everything, including
  GitHub.
- 01:42 - the session force-kills the owner's running Chrome
  (`Stop-Process -Force`) without asking, to run a logging diagnostic -
  an unconsented action on an already-wounded profile.
- 02:0x - repair with owner consent: `Web Data.token_service` held
  exactly one stale token row (the failing account); it was deleted
  after a backup was taken. The backup directory was later deleted on
  the owner's instruction.

## The root errors, in the owner's framing and confirmed by audit

1. **A full Desktop with official operational surfaces was run for a
   step that did not need it.** The load-proof goal did not require the
   onboarding/login-bearing app; a CLI or dev-agent verification would
   have served. The official login+activity surface added zero PoC
   value and created the entire risk window.
2. **The GUI ran before its own instruction existed.** Launching a
   login-demanding window and writing the guidance afterward is not a
   control - an instruction that reaches the human after the risk
   window is not an instruction. Any GUI-touching step must be
   instruction-first, then launch, then wait-for-human
   (views/workflows/human-in-the-loop-wait.md exists and was violated
   in spirit by this very session one turn before writing it).
3. **Isolation theater.** The scratch-profile/env-var isolation
   protected the filesystem (audited: zero writes to the real Chrome
   profile by any of the 535 tool calls) but not the process ecosystem
   the owner was actively using: env inheritance leaks to anything the
   app launches; process-tree kills had unbounded, unattributable blast
   radius with truncated outputs during the exact window Chrome broke.
   Confidence in "isolation" outran the evidence.
4. **The unconsented force-kill of the owner's Chrome** - a second
   unclean shutdown applied to a damaged profile during "diagnosis".
5. **Overconfident claims**: "everything is normal" (assessed from file
   existence only, later contradicted by the owner's experience), and a
   speculative "delete your passkey" recommendation later retracted
   (inference presented as fact).

## What cannot be proven

The exact event that invalidated the browser's key state sits inside
the session's activity window (00:58-01:42) but was never captured. The
audit proves no direct profile write; it cannot prove the indirect
chain (popup forwarding, restart storm, kill blast radius) was
harmless. The session records this gap honestly instead of resolving
it in its own favor.

## Binding lessons

- GUI-bearing PoC steps: instruction BEFORE launch, explicit
  wait-for-human, and a stated "you will see X, do nothing until told".
- No official onboarding/login surfaces inside PoC profiles, ever;
  prefer CLI/dev-agent verification for every claim that does not
  strictly require the GUI.
- Never kill or restart owner-visible processes without consent, even
  for diagnosis.
- Env isolation is filesystem-only containment; treat the process
  ecosystem and the human's live desktop as inside the blast radius.
- A message is not delivered until the human has seen it; sequencing of
  human-visible guidance is part of the safety envelope, not an
  afterthought.
