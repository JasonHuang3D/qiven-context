# Apply known engineering architecture directly instead of reproducing human trial-and-refactor history

Qiven's AI-led development process must not treat avoidable code debt as a learning mechanism. The first serious implementation should use already-established engineering knowledge to choose correct semantic ownership, dependency direction, ownership/lifetime, resource bounds, failure behavior, concurrency semantics, and performance structure before substantial product-local code is written.

A downward dependency is not a defect merely because it increases repository coupling. When layer `A` needs a capability whose natural semantic owner is lower layer `B`, improve `B` first and make `A` consume it. Do not create a reduced duplicate in `A` solely to keep `A` temporarily self-contained and plan to refactor later.

Multiple consumers are useful evidence but are not a prerequisite for correct placement. One concrete downstream need can reveal a missing foundational/runtime/network primitive when its semantic ownership is already clear.

Foundation remains strict and product-free. Capabilities that are below a product but above Foundation belong in a lower shared layer such as Runtime or Networking rather than being duplicated in the product or forced into Foundation.

Experiments, compiler feedback, benchmarks, and tests are for genuine unknowns and proof. They should not be used as theater to rediscover mature engineering principles that can be applied directly.

This doctrine is normative through `collaboration/software-engineering-philosophy.md` and ADR-0024 and must be considered before implementation begins on architecture-sensitive code.
