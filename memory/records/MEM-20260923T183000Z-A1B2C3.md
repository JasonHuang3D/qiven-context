# The heredoc rule recurred: an active record that cold boot never read

Root cause of the 2026-09-23 recurrence: NOT in-session memory loss. The
rule existed and was `active` (MEM-20260921T203500Z-D2A7F4) but lived in
`memory/records/` — reachable only through retrieval, and the sealed
retrieval tooling means the READING agent must invoke it. The cold-boot
checklist read state and collaboration files but never swept
`memory/index.yaml`, so a standing discipline record was operationally
invisible — constitution §16 verbatim: a correct retrieval engine that
is not invoked is a retrieval miss. The session then authored many files
via python heredocs, and the channel's escape-eating (`\\n` became a
literal newline) corrupted two operator patches in one turn — the same
defect class the rule exists to prevent, striking while fixing the rule
itself.

Fixes landed the same turn:

1. BOOTSTRAP step 14 now REQUIRES reading `memory/index.yaml` and
   treating active titles as binding standing knowledge.
2. The rule is restated in a boot-read contract
   (`collaboration/operating-contract.md`, "File-authoring tool
   discipline") so it no longer depends on retrieval being invoked.
3. This record extends D2A7F4 with the mechanism understanding: the
   tool channel interprets escape sequences inside heredocs — heredoc
   authoring is not merely error-prone, it is mechanically corrupting
   on this harness; native file tools are the only authoring path.
