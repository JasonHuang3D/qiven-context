# Treat upstream conversational execution as potentially split-brain and enforce single-writer authority on the host

A conversational AI/UI must not be treated as the enforcement point for machine-local single-writer semantics. During Qiven-v4 the project owner observed two answer choices concurrently driving the same DCR/MCP-connected JasonPC despite the intended single-flow workflow.

The upstream product mechanism is not established by Qiven, but the engineering consequence is established: local safety cannot depend on there being only one assistant response, one tool caller, or one surviving UI branch.

DCR's observed recent-call history does not provide a stable assistant-response/caller identity, so a split-brain event cannot be reliably reconstructed or fenced after the fact from chronology alone.

JasonPC local execution therefore requires a host-side authority broker with exclusive per-response execution transactions, leases, monotonic fencing epochs, strict request sequencing/idempotency, quarantine when a competing authority appears, and reconciliation before authority is reissued after uncertainty.

A second contender must be rejected rather than queued for later execution. Once concurrency is detected, continuing either flow without reconciliation is unsafe because exact-head, clean-tree, fail-fast, and repository-state assumptions may already have diverged.

Until that broker is accepted, mutating DCR use is suspended; read-only incident forensics remain acceptable.
