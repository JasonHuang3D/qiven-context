# Official DCR terminal history is per-session bounded but aggregate completed-session retention is not byte-bounded

The installed Desktop Commander 0.2.50 `TerminalManager` caps retained output for one process session at approximately 50 MiB, but copies completed-session output into a history capped by the last 100 sessions by count. No smaller aggregate byte budget or TTL was found in the installed implementation.

An isolated harness using the same installed implementation showed resident-memory growth as completed output accumulated: about 119.7 MiB RSS at baseline, 208.2 MiB after about 56 MiB retained output, and 304.1 MiB after about 105 MiB retained output.

The model-facing `start_process` wait output remained around 1 MiB during the same synthetic runs, so caller-output protection and server-internal completed-session retention are separate boundaries.

After the project owner restarted DCR, the fresh live remote-device and local-MCP Node processes returned to roughly 100 MiB working set each. Restart is therefore an effective in-process resource-reclamation boundary for this failure mode.

For Qiven DCR Windows V1, hiding the console is insufficient. The native supervisor must continuously drain pipes, keep UI/disk queues byte-bounded, monitor the exact owned process generation, and treat controlled restart as a legitimate resource-reclamation action. Soft pressure must not silently interrupt active work; hard host-protection restart must surface truthful interruption/failure rather than success.

Numeric memory thresholds remain operational/test parameters until V1 workload evidence stabilizes them.
