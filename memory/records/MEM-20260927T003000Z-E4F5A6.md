# Scope-bound path matching

Two defects in one lexical governed-path matcher, found by the MVP-4
simulated gate's first dev runs (2026-09-26):

1. The original match required the governed path to be followed by "/",
   so an absolute target naming a governed FILE exactly
   (`<root>/state/current.md`) never matched — only children of DIR
   entries did. A governed-file write was silently ungoverned.
2. The first fix (pure suffix matching) over-governed: an OUTSIDE tree
   that repeats the relative suffix (`<outside>/state/current.md`) was
   denied too, because the suffix carries no root identity.

The correct shape for lexical scope matching of relative paths against
absolute targets: match the relative exact form (`target == path`) and the
absolute form BOUNDED by the governed root prefix (`starts_with(root)`
plus `ends_with("/" + path)` — the leading separator is the boundary, so
`current.md.bak` and `notstate/current.md` cannot match); keep
containment-anywhere only as deliberately labeled over-approximation.
The same law applies to any string-scoped authorization: a suffix
without its root bound is not a scope, and a separator requirement
without an exact form is not a file policy.

General lesson: an acceptance rig built from incident evidence finds
oracle errors and real defects together; classify every first-run failure
before fixing (the 55-failure first run decomposed into rig-oracle errors
plus exactly one real host defect, and fixing in the wrong order produced
defect 2 from fix 1).
