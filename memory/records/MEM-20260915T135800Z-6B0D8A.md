# Treat the observed roughly 26-minute Chat/DCR turn boundary as an operational checkpoint budget

During Qiven-v4, the project owner observed four consecutive long-running turns terminate at roughly 26 minutes or slightly beyond. One earlier interruption had coincided with a failed Clash upstream node, but repeated later observations made a transport-node explanation insufficient.

The underlying ChatGPT product mechanism is not established here. This record does not claim whether the boundary is caused by wall-clock execution limits, tool-runtime policy, conversation limits, UI behavior, or another internal constraint.

For Qiven engineering, the repeated observation is sufficient to treat a single long Chat/DCR turn as a finite execution window. Long tasks should therefore create durable intermediate state continuously and aim to reach a coherent checkpoint before approximately 20-22 minutes rather than depending on work that exists only near the end of a turn.

A turn cutoff is treated like any other transport interruption: do not infer that already-dispatched local or remote work failed; reconcile authoritative Git, filesystem, process/session, and DCR state before replaying or continuing.

This is an operational budget, not a permanent platform law. Reassess if future repeated observations materially change the boundary.
