# Resume Qiven Operator Phase 1 after Qiven-v1 session rollover

The active implementation branch is `jason-brother/devkit-operator-phase1`. Qiven-v1 closed at `ac816bb06fbe978c1b41a730104114e8f5778610`, where the remaining failure log had not yet been preserved.

Qiven-v2 recovered the exact failure from the owner. `cmd-control-flow`, `adoption-missing-sync`, and `operator` passed; `devkit-regression` failed with `Foundation-shaped plan omitted .clang-format`. Source review established that the historical Foundation-shaped fixture deleted `.qiven` to simulate an unadopted repository and then appended drift to every non-exact managed path. Once `.qiven/operator.json` became managed, that loop recreated `.qiven`, causing the adoption precondition to reject the repository before emitting a plan.

Commit `cc463495845e57f68d54b535d7a64c8a293bc652` repaired only that fixture model: the three historical exact paths remain exact, `.qiven/operator.json` is correctly modeled as missing for an unadopted repository, and the other managed paths remain conflicting. The owner then reported `tools/test.cmd` ALL PASS on that exact head, and jason-brother verified the remote active branch still pointed to the same SHA.

The successful run also reinforced an existing human-interface requirement: a long-running CLI can still feel ambiguous while the operator waits. CMD remains a thin transport. Python Operator owns truthful start/progress/heartbeat feedback, stable status layout, buffered failure detail, and final summary; this is part of Phase 1 dogfood acceptance rather than a reason to rebuild orchestration in batch files.

Phase 1 therefore advances from regression repair to Operator dogfood. No merge, template `0.1.3` release, or Foundation/Math Operator synchronization has occurred yet. Any new Devkit commit after `cc463...` requires fresh local validation before ADR-0021 merge authority applies to that new head.
