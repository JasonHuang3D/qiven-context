# Use explicit @qiven plus Remote Desktop Commander as the Phase 1 Chat-mode execution transport

## Context

ADR-0022 established that retrieval capability is insufficient unless retrieval is invoked reliably. The project then evaluated which ChatGPT surfaces available to the current Plus account can provide a practical execution boundary for the canonical local `qiven-context` runtime without replacing normal Chat with a custom host.

The research established that automatic Skill routing is not reliable enough to be a safety boundary, explicit Skill selection is per-turn and observable, WebMCP Site Tools currently require the Work surface for the tested path, and a private custom Qiven Plugin/MCP is not available as the immediate Plus workflow. Using GitHub as an asynchronous mailbox would technically bridge Chat to a local worker, but would add avoidable latency, failure modes, and misuse Git as an RPC transport.

The published Remote Desktop Commander plugin, however, successfully connected normal Chat to the authorized `JasonPC` Windows machine and executed local terminal commands against `D:\JasonWork\qiven-context`.

A latency study also showed that Remote Desktop Commander should be considered a high-latency transport: local work was sub-second while a complete remote tool call was observed around twenty seconds. Therefore transport granularity is part of the reliability architecture.

## Decision

For Qiven Context Phase 1 in normal Chat mode:

1. **Explicit invocation gate.** Qiven cognition turns that depend on canonical project history must be explicitly invoked with `@qiven`. Automatic Skill routing is not trusted and invocation is not assumed to persist across turns.
2. **Remote Desktop Commander is the Phase 1 execution transport.** The Skill may use the published Remote Desktop Commander plugin to reach the explicitly authorized `JasonPC` local runtime. GitHub remains source control and evidence transport, not the execution RPC path.
3. **One coarse-grained runtime call.** A Qiven preflight must execute one local command that performs retrieval, obligation handling, provenance capture, and Context Lease creation locally, returning one machine-readable result. The LLM must not orchestrate a chatty sequence of remote file reads and subprocess calls.
4. **Canonical runtime stays local and singular.** The implementation executed through the transport is the canonical `qiven-context` runtime on JasonPC. Skill-bundled scripts, Sites, or duplicated cloud implementations must not become a second canonical runtime.
5. **Fail closed.** If explicit Skill invocation, Remote Desktop Commander availability, local execution, result validation, or Context Lease issuance fails, the assistant must not substitute model-native memory, stale conversation context, or guessed repository facts for the missing preflight.
6. **Concurrency is not yet accepted.** Serial explicit invocation has passed repeated probes; concurrent fresh-Chat invocation exposed at least one tool-availability failure. Phase 1 therefore assumes one active Qiven cognition turn at a time until concurrency is independently measured and accepted.
7. **Scope local authority narrowly.** The Qiven cognition path should treat Remote Desktop Commander as a transport to the Qiven Context runtime, not as general permission to modify the host. Default preflight should read/execute within the Qiven Context boundary and must not opportunistically alter system configuration or unrelated files.
8. **Source synchronization precedes production lease acceptance.** The local qiven-context clone must be intentionally synchronized to the accepted canonical head before the transport is accepted for production Context Leases.

## Alternatives Considered

### Rely on automatic Skill routing
Rejected. A relevant Qiven turn can proceed without automatic Skill activation, so it cannot guarantee preflight invocation.

### Use GitHub as a request/result mailbox to a local worker
Rejected for Phase 1. It would route runtime RPC through source control, increasing latency and introducing polling, synchronization, and delivery failure modes even though a direct published execution plugin is available.

### Use WebMCP Site Tools
Deferred as a Work adapter. The technical WebMCP probe succeeded, but the tested Site Tools path was not available as the desired normal-Chat execution surface.

### Build a private Qiven Plugin or custom MCP
Deferred. The current Plus product surface does not provide the private self-import path required for the immediate workflow. The architecture should remain adapter-friendly so this can replace Remote Desktop Commander later.

### Put the Context Runtime inside Skill scripts
Rejected as the canonical design. This would create a second implementation/runtime packaging surface and risk drift from the repository-owned Qiven Context runtime.

### Build a custom conversation host around the OpenAI API
Deferred. It could enforce preflight mechanically but would sacrifice the current native ChatGPT experience and require rebuilding conversation, memory, and connector integration before evidence shows that cost is necessary.

## Consequences

The immediate engineering target becomes a stable local preflight entry point with a narrow machine-readable contract. Remote Desktop Commander only needs to execute that entry point once per required retrieval boundary.

The measured remote orchestration overhead also means future optimization should favor Context Lease-aware reuse at explicitly accepted boundaries rather than multiplying remote calls. Reuse remains an optimization and must never make the reasoning model responsible for remembering whether retrieval is required.

Remote Desktop Commander is an adapter, not a permanent architectural dependency. A future native custom MCP/App, WebMCP Chat capability, or other trusted execution transport may replace it without changing `qiven.context.prepare` or canonical storage.

## Revisit Conditions

Revisit this transport choice when any of the following becomes true:

- the current Plus surface permits a private Qiven custom MCP/App with reliable Chat-mode invocation;
- WebMCP Site Tools become available and reliable in normal Chat;
- Remote Desktop Commander becomes unavailable, unstable, insecure for the required scope, or its latency materially degrades user experience;
- measured concurrency or invocation behavior justifies relaxing the single-active-turn constraint;
- a custom host becomes justified by requirements that native Chat can no longer satisfy.

## Provenance

Accepted after direct probes of Skill activation, live GitHub nonce retrieval, fail-closed behavior, serial/concurrent invocation, WebMCP Site Tools, Remote Desktop Commander normal-Chat command execution, and a layered network/runtime latency diagnosis. Detailed measurements and observed product-surface boundaries are preserved in `evidence/research/chat-invocation-runtime-2026-09-15.md`.
