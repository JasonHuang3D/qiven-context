# Select GitHub CI validation explicitly after remote review

## Context
Qiven uses local implementation validation and a later cross-platform GitHub CI release gate. The team deliberately separated the question of what needs validation from the mechanics that execute validation.

## Decision
GitHub CI is manually dispatched rather than automatically triggered by every push. jason-brother reviews the exact remote delta and chooses the validation scope. Repositories expose deterministic validation units that can run as a selected subset or as `full`; invalid selections fail rather than being guessed.

CI executes the requested plan. CI does not infer architectural relevance from changed files and does not decide which validation units are sufficient.

## Alternatives Considered
Automatic push-trigger full CI for every branch update; path/diff-driven CI that autonomously decides which jobs are relevant; treating local validation as sufficient release evidence.

## Consequences
Cross-platform compute is spent deliberately, review remains the authority for validation scope, and the same workflow can execute narrow or complete plans deterministically. The team must remember to dispatch CI when required, so that responsibility is part of the review protocol rather than an automatic side effect of push.

## Revisit Conditions
Revisit if Qiven reaches a scale where deterministic dependency metadata can prove validation scope more reliably than human review, or if CI economics make full automatic validation the clearly superior default without reducing review quality.

## Provenance
Genesis reconstruction from the committed workflow-dispatch CI implementations in Foundation, Math, and Devkit plus the Foundation worker protocol that treats GitHub CI as a later CTO-reviewed release gate.
