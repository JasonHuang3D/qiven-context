# Treat C++ object layout, ABI, IPC, wire, and persistent representation as separate boundaries

## Context
Qiven will cross module, process, shared-memory, network, and persistent-storage boundaries. Reusing native C++ representation across those boundaries would leak process-local pointers, platform-sized values, host byte order, compiler layout, or module lifetime into formats that require transferable identity and compatibility.

## Decision
An in-memory C++ representation is local unless an explicit boundary contract says otherwise. A Foundation C++ API is not automatically a stable module ABI, IPC representation, wire format, shared-memory format, or persistent format.

Cross-process/network/persistent boundaries define their own transferable representation, including fixed integer widths, byte order where relevant, validation, compatibility, and versioning. Process-local pointers, callback/function addresses, native handles, `usize`/`isize`, and ambient object identity are not portable transferable identities.

Before 1.0, Foundation does not promise a stable C++ binary ABI; binary compatibility boundaries are introduced only for concrete distribution/plugin requirements.

## Alternatives Considered
Serializing or sharing native object layout directly; treating source compatibility as binary compatibility; using platform-sized fields or native pointers in persistent/wire formats because they are convenient in-process.

## Consequences
Boundary code is more explicit and may require conversion/copying, but representation contracts become portable, versionable, and reviewable. Native implementation layout can evolve before 1.0 without accidentally redefining wire or persistence semantics.

## Revisit Conditions
Revisit when a real plugin/distribution/shared-memory requirement demands a stable ABI or mapped representation; design that boundary explicitly rather than broadening native C++ layout into an implicit contract.

Genesis reconstruction from the committed Foundation representation/boundary law and ABI policy.
