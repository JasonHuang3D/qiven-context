# Devkit owns Qiven native build-system mechanism while repositories own declarative build graphs

## Context

Native repositories need consistent compiler policy, dependency resolution, test registration, lifecycle tooling, and build-system compatibility without duplicating mechanism or replacing CMake with a Qiven-specific language.

## Decision

`qiven-toolchain-win` owns executable tools. `qiven-devkit` owns shared native build and engineering mechanism, distributed through `templates/native-common/managed`, with `cpp-library` and `cpp-app` profiles. Repositories own ordinary declarative CMake graphs using `add_library`, `add_executable`, `target_sources`, and `target_link_libraries`.

Devkit's shared modules are `QivenBuild.cmake`, `QivenProject.cmake`, `QivenTarget.cmake`, `QivenDependency.cmake`, and `QivenTest.cmake`. They own policy/mechanism, strict argument validation, dependency option scoping, test policy, and an explicit build-system API compatibility handshake. Repository snapshots remain independently buildable.

## Alternatives Considered

- Give every repository an ad-hoc CMake policy layer. Rejected because it duplicates semantics and drifts.
- Build a replacement language over CMake. Rejected because repository graphs should remain ordinary, inspectable CMake.
- Put executable tool ownership in Devkit. Rejected because toolchain artifacts belong to `qiven-toolchain-win`.

## Consequences

Shared improvements are made once in Devkit and propagated through the managed lifecycle. Repositories retain control of targets and dependency edges. Exceptions, RTTI, SIMD, LTO, sanitizers, and global Windows definitions require separate real contracts.

## Revisit Conditions

Revisit when CMake can no longer express an accepted requirement or a shared mechanism proves repository-specific.

## Provenance

Canonicalizes the Native Build System architecture developed and dogfooded during Qiven-v4 before the split-brain incident interrupted candidate closeout.
