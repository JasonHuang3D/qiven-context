# Resolve qiven-foundation as an existing local source dependency without network CMake fetching

## Context
qiven-math depends on Foundation types/contracts but should remain deterministic in local development and CI without hiding package acquisition or network side effects inside configure-time logic.

## Decision
Dependency resolution follows this order: reuse an already-defined `qiven::foundation` target; otherwise use explicit `QIVEN_FOUNDATION_ROOT`; otherwise use sibling `../qiven-foundation`. The selected source tree is validated before `add_subdirectory`.

qiven-math does not use `FetchContent`, vendored Foundation copies, submodules, or network acquisition as the default CMake dependency path in this phase. When Math brings Foundation in as a subdirectory, Foundation tests are disabled through normal variable shadowing around `add_subdirectory`, not by mutating persistent cache state with `CACHE ... FORCE`.

## Alternatives Considered
Configure-time network FetchContent; vendoring a Foundation copy; Git submodule coupling; forcing Foundation's cache test option from Math.

## Consequences
Workspace composition remains explicit and offline-friendly. CI or developers must provide Foundation locally or in the expected sibling layout. The build does not silently download dependencies or permanently overwrite consumer cache policy.

## Revisit Conditions
Revisit when Qiven establishes a deliberate package/distribution model or workspace composition layer that provides a stronger dependency contract than local source composition.

## Provenance
Current CMake mechanically verifies the target/root/sibling source-resolution flow and non-cache test suppression. The explicit no-FetchContent rationale is retained from retrospective project discussion and is not inferred solely from absence in CMake.
