# Define ContextKernel as the representation-independent semantic authority behind Qiven Context

## Context

The accepted Context v2 repository proves participant-independent continuity,
canonical lifecycle, immutable reads, provenance, protected constraints and
ContextView adaptation. Its current physical representation is Git-versioned
Markdown, YAML and JSON. That representation remains inspectable and reliable,
but canonical transactions, indexing, retrieval and coordinated updates become
increasingly expensive as the number of providers, consumers and records grows.

The next architecture must not mistake a database product, local executable,
service process, vector index or file layout for Context itself. Git, a filesystem,
process memory, SQL, Redis, an object store and future representations are possible
mechanisms beneath one semantic contract. `qiven-context.exe` is an entrypoint into
that contract, not the owner of project truth merely because it is running.

The architecture must preserve the already accepted properties:

- project truth is identity-independent;
- evidence and canonical interpretation remain distinct;
- lifecycle and conflict resolution are explicit and historical material survives;
- reads are snapshot-bound and derived retrieval is never canonical;
- ContextView adapts interaction without overriding ProjectContext;
- retrieval never grants execution or governance authority;
- GitHub remote remains canonical until a separately accepted cutover proves a
  replacement authority boundary.

## Decision

### 1. Semantic owner and process boundary

Define **ContextKernel** as the representation-independent owner of Context
semantics. The kernel is a library/domain boundary, not a daemon requirement and
not a storage engine.

The dependency direction is:

```text
provider / consumer clients
        -> command and query ports
        -> ContextKernel semantic model
        -> storage, identity, clock and retrieval ports
        -> Git / files / memory / SQL / object store / future adapters
```

`qiven-context.exe` is initially a thin CLI and local-process facade over the same
kernel commands and queries. A long-running service, IPC endpoint, MCP surface or
remote API may be added only when a concrete multi-client or latency requirement
justifies it. No transport receives independent semantics.

### 2. Canonical semantic objects

The kernel operates on the following representation-independent concepts:

| Concept | Semantic responsibility |
| --- | --- |
| `ProjectId` | Stable identity of one independent project context. |
| `RecordId` | Stable logical identity of an ADR, memory, obligation or another registered canonical record kind. |
| `RecordRevision` | Immutable typed payload plus lifecycle, temporal, relation and provenance metadata for one record revision. |
| `EvidenceObject` | Immutable raw or external evidence reference with media type, digest, provenance and availability semantics. Evidence is not automatically canonical interpretation. |
| `ProjectSnapshot` | Immutable, content-identified closure of record revisions, project/state documents, governance, views and required contracts visible to one read transaction. |
| `ContextTransaction` | Atomic proposed change from exactly one base snapshot to one successor snapshot. |
| `ContextViewSpec` | Durable participant/environment/workflow adaptation that cannot override ProjectContext truth or governance. |
| `ContextQuery` | Typed, explicit consumer request including scope, history mode, time, completeness claims and evidence for negative inputs. |
| `ContextBundle` | Immutable snapshot-bound delivery of mandatory context, protected constraints, selected evidence, diagnostics and provenance. |
| `AuthorityDecision` | Separate allow/deny result for a proposed mutation, evaluated against authenticated principal, governance version and operation. It is never inferred from a bundle. |

Record kinds remain extensible only through registered schema and lifecycle policy.
An unknown kind or state fails closed; it does not silently degrade into an
untyped document.

Every immutable object has a semantic digest over canonical serialization. A
storage locator, row identifier, path, Git SHA or memory address may be preserved
as provenance but is not the semantic identity contract.

The hash dependency is acyclic. `transaction_id` is an opaque, project-scoped
unique identifier allocated before hashing, not a transaction digest. Evidence
and prior revisions are hashed first; new revisions refer to that opaque ID and
prior revision digests, never to the creating transaction's digest or its successor
snapshot. The successor snapshot hashes its ordered content manifest and base
snapshot digest, not the creating transaction digest. A transaction receipt then
hashes the request digest, base/successor snapshot digests, revision digests and
commit-time authority decision. The committed transaction-ID-to-receipt mapping
is immutable and published atomically with the head. A successor links backward
to prior history; no object includes its own digest in its hashed payload.

Before K1 acceptance, a versioned serialization contract must enumerate each
object's hashed fields, type/domain separators, ordering, absent/null distinction,
Unicode and numeric rules, and digest algorithm, with golden vectors. Canonical
payload and asserted provenance are hashed; adapter locators and runtime timings
are outside the semantic payload. Preserved Git identities are immutable source
provenance, not replacement semantic IDs. No unversioned serializer defaults may
determine identity.

### 3. Revision, lifecycle and provenance semantics

Canonical mutation never overwrites historical meaning in place. Revising a
logical record creates a new `RecordRevision`; a `ProjectSnapshot` selects the
visible revision. Lifecycle transitions remain explicit domain operations and
must satisfy the accepted reciprocal, acyclic supersession graph.

Each canonical revision preserves:

- logical record identity, kind and schema version;
- lifecycle status and transition rationale;
- typed payload/body;
- scope, tags, relations and temporal validity;
- provenance sources and evidence digests;
- creating transaction and predecessor revision when one exists;
- authenticated actor assertion and authority decision reference for native
  mutations; explicit historical authentication status for imported revisions;
- canonical serialization version and semantic digest.

Provider assertions retain epistemic type. Observation, hypothesis, proposed
decision, accepted decision and verified fact are not interchangeable merely
because they share a storage table or API.

Git import preserves historical author/committer metadata as unverified source
assertions unless separate authentication evidence exists. Missing historical
principal or authority evidence is explicitly `unknown`, never synthesized from
Git names/emails. The current import actor and import authorization belong to the
import receipt, not to the historical action. Unsupported historical semantics
remain explicit blockers to equivalence; import cannot upgrade old assertions.

### 4. Transaction model

A material Context change is one atomic transaction. It declares:

- `transaction_id` and caller-supplied idempotency key;
- exact base `ProjectSnapshot`;
- authenticated principal and requested operation/intent;
- explicit ordered semantic operations;
- referenced evidence and expected record revisions;
- explicit clock input where time affects semantics;
- governance version used for authorization.

The minimum operation vocabulary is:

- create or revise a canonical record;
- transition lifecycle;
- create or remove a typed relation;
- add immutable evidence or an external evidence reference;
- update compact project state;
- create or revise a ContextView specification;
- close, supersede or create an obligation;
- publish a new snapshot if every invariant and authority check passes.

Commit uses compare-and-swap against the declared base snapshot. A stale base,
changed expected revision, duplicate idempotency key with different content,
failed invariant, missing evidence, unsupported schema or denied authority aborts
the entire transaction. The kernel never performs a silent field-level merge and
never exposes a partially committed canonical snapshot.

An idempotency key is scoped by project and authenticated principal and bound to
a versioned digest of the complete request (base, ordered operations, evidence,
expected revisions, explicit semantic time and requested governance version).
The same key and request returns the original committed result, including its
successor snapshot, even when the head has since advanced; it does not re-execute
or fail merely because the original base is now stale. Different content under
the same key is rejected. Keys and committed results are durable for the retained
transaction history; no silent expiry or key reuse is permitted.

The adapter atomically publishes transaction receipt, idempotency result and head
CAS. A definite pre-commit rejection returns `not_committed`. A timeout or lost
acknowledgement after a possibly successful commit returns `outcome_unknown`, not
an assertion of rollback. `GetTransactionResult` reads the durable outcome from
the authoritative adapter; absence during an in-flight operation is not proof of
abort. A same-key retry must serialize with that operation and resolve to at most
one commit. While unresolved, dependent mutations stop; retry with a new key is
not recovery. Evidence staged before commit may remain unreferenced but is never
visible as canonical state. Abort cannot undo an already committed transaction.

Authorization binds project, authenticated principal, complete request digest,
base snapshot, operation scope and governance version. Proposal validation is
advisory, not a reusable grant. Immediately before commit, the kernel rechecks
authorization against the base snapshot's existing governance and the identity
provider's current authentication/permission result; head CAS rejects intervening
canonical governance changes. Governance updates must be authorized by the old
policy, never by their proposed replacement. Expired, revoked, mismatched or
unverifiable grants are rejected. External revocation cannot be made atomic with
storage by assertion: each adapter must document its check point and residual
check-to-commit window. Current GitHub publication also enforces GitHub's live
permissions at the remote mutation boundary; stronger cross-provider fencing is
required before any cutover claiming stricter revocation guarantees.

The semantic transaction history is not a second manually maintained event log.
It is the durable chain of immutable transactions/revisions required to explain
successor snapshots. A representation may store that chain as Git commits, rows,
objects or another mechanism.

### 5. Provider command surface

Provider is a role, not an authority class. Humans, agents, CI, repositories and
runtime systems may all provide evidence or proposals.

The logical command surface is:

- `SubmitEvidence` — store or reference immutable evidence without promoting its
  claims to canonical truth;
- `ProposeTransaction` — construct and validate a candidate against a base
  snapshot without changing the canonical head;
- `ValidateTransaction` — return typed invariant, schema, conflict, provenance and
  authority diagnostics;
- `CommitTransaction` — atomically advance the canonical head only after positive
  authentication and authorization;
- `AbortTransaction` — terminate a candidate without side effects;
- `GetTransactionResult` — resolve a same-key request's durable outcome without
  performing another mutation, subject to the caller's access policy;
- `ImportSnapshot` — ingest a self-describing export into a non-authoritative or
  explicitly selected project namespace;
- `PromoteAuthority` — a separately governed cutover operation, never a side
  effect of import, restore or successful startup.

Commands return typed results such as stale base, conflict, unauthorized,
invalid lifecycle, unsupported schema, incomplete evidence and storage failure.
Unknown or ambiguous outcomes block dependent work without claiming rollback.

### 6. Consumer query and ContextBundle surface

Consumers read one exact snapshot, either explicitly named or resolved once from
the current canonical head at query start. One query cannot mix record revisions,
governance or indexes from different snapshots.

The minimum query surface is:

- get a record and its revision/provenance;
- inspect current or historical lifecycle state;
- follow typed relations and supersession chains;
- diff two snapshots or revisions;
- evaluate non-terminal obligations using explicit evidence and three-valued
  unknown semantics;
- compile identity-independent ProjectContext;
- compile a declared `ContextView` from ProjectContext plus view inputs;
- build a bounded `ContextBundle` with mandatory inputs, protected constraints,
  ranked candidates, omissions and diagnostics;
- explain why material was included, excluded or unresolved;
- export one complete snapshot for backup, migration or audit.

`ContextBundle` remains evidence for reasoning, not truth resolution or permission.
It always carries snapshot identity, source/evidence digests, schema versions,
selection explanations and `authorization: not_granted`, without exception.
A higher-level caller may carry a separate `AuthorityDecision` alongside the
bundle in an operation envelope; it must not alter the bundle or turn retrieval
into permission. That decision binds the exact mutation under section 4 and is
checked again at execution. The kernel does not infer authenticated identity
from natural-language query text.

### 7. ContextView compilation

View resolution and bundle construction are distinct stages. View resolution is
a deterministic pure transformation of:

```text
ProjectSnapshot
+ ContextViewSpec
+ explicit live capability/environment assertions
+ evidence describing which assertion sets are complete
+ explicit clock
-> ResolvedContextView
```

Durable view declarations may select presentation, workflow and environment
profiles. Mutable versions, paths, connectivity and runtime capabilities remain
live inputs and must be verified when material. Missing or invalid referenced view
material fails the compilation; an absent optional view falls back to
identity-independent ProjectContext rather than inventing adaptation.

Bundle construction consumes that resolved view, the same snapshot, the complete
ContextQuery (including history/explicit IDs and budgets), explicit semantic time,
and a versioned retrieval/selection configuration. Reproducibility requires the
same deterministic backend or the same captured candidate IDs/scores and ordering
for a nondeterministic backend. Backend/model identities alone do not guarantee
repeatability. Runtime timings are external. Existing R1 mandatory-input,
protected-constraint, whole-record budget and unknown-input rules remain binding.

### 8. Derived retrieval and indexing

Lexical, FTS, BM25, embedding, vector, graph, structural and reranking indexes are
replaceable derived projections. Every index is bound to an exact snapshot and
records its model/algorithm/configuration identity.

An index may return candidate identifiers and scores. Canonical payload and
provenance are always rehydrated from the selected snapshot. Index lag, corruption
or unavailability must produce an explicit diagnostic, fall back to an accepted
deterministic path when possible, or fail visibly. It must never cause a query to
silently read a different snapshot or promote ranking output into canonical truth.

### 9. Storage port

The kernel requires capabilities, not a product-specific interface. A canonical
storage adapter must provide:

- immutable object put/get by semantic digest;
- snapshot and revision lookup;
- atomic publication of transaction receipt, idempotency result and
  compare-and-swap of the canonical head;
- authoritative transaction-result lookup and serialization of same-key retries;
- durable governance/authority-decision references;
- consistent read of one selected snapshot;
- enumeration needed for deterministic export and invariant validation;
- explicit durability and failure reporting.

Optional adapter capabilities such as native full-text search, graph traversal,
leases, notifications or incremental backup cannot change kernel semantics.
The first implementation may use memory or the existing Git/filesystem model as
a reference adapter. SQL, Redis and object storage are not selected by this ADR.

### 10. Canonical export, backup and restore

The portability boundary is a self-describing **Canonical Context Export**, not a
database dump. It separates a stable semantic manifest from an evidence delivery
package. The semantic manifest contains:

- project and snapshot identities;
- all reachable canonical record revisions and required documents;
- lifecycle relations and transaction ancestry needed to interpret the snapshot;
- governance and ContextView specifications;
- immutable evidence descriptors, expected digests when known, and historical
  provenance; external references with unknown content digests remain unknown;
- schema/serialization versions, ordered manifest, per-object digests and root
  semantic digest;
- no credentials, tokens, private keys or recovery secrets.

For the same snapshot and export format version, semantic manifest generation is
deterministic. A separate package manifest lists included evidence bytes, their
digests, omissions and reasons, export access policy and availability observation.
Its package digest may differ across exports without changing the snapshot's
semantic root. Live availability never rewrites an immutable evidence descriptor.

No secret may enter native canonical payloads; secret-bearing historical source
blocks complete export until separately governed remediation. Required canonical
objects cannot be silently redacted while claiming an identical semantic root.
Evidence bytes may be omitted with explicit diagnostics; such a package proves
manifest integrity only, not full evidence recoverability. Export validates raw
bytes against known digests and reports unverifiable external references.

Restore into an empty adapter validates the semantic root and package integrity
independently and reports completeness against an explicit recovery profile.
Missing objects required for ProjectContext, protected constraints, governance,
provenance verification or the declared continuity acceptance corpus block full
recovery acceptance. Partial restores remain quarantined and cannot satisfy
cutover. A cutover ADR must enumerate permitted external-evidence dependencies
and prove their recovery path; matching root digests alone is insufficient.
Optional incremental backups identify an exact base export and never replace the
ability to produce periodic complete exports.

Restore creates a quarantined, non-authoritative project instance by default.
Successful checksum validation, import or query execution does not make the
restored instance canonical. Promotion requires explicit governance authorization
and the authority-cutover protocol below.

### 11. Migration from Git and authority cutover

Migration is staged and single-authority. Independent canonical dual-write is
forbidden because it creates two truths without an atomic cross-system commit.

1. **Import proof** — import an exact Git commit into ContextKernel while
   preserving raw source, record IDs, lifecycle, provenance and Git identity.
2. **Read equivalence** — for a fixed acceptance corpus, current Git tooling and
   the engine produce semantically equivalent mandatory inputs, protected
   constraints, lifecycle qualification, evidence and ContextBundles. Ranking
   scores need not be byte-identical when the candidate contract only requires
   equivalent protected coverage and supported conclusions.
3. **Export/restore proof** — export the imported snapshot, restore into an empty
   adapter, verify the semantic root and rerun Project Continuity.
4. **Shadow operation** — ingest canonical Git changes and exercise engine reads
   while GitHub remains the sole authority. Divergence is a blocker, not an
   invitation to choose whichever result is convenient.
5. **Write-path proof** — engine transactions deterministically export a complete,
   reviewable Git-compatible projection or another accepted audit projection,
   without losing provenance or lifecycle meaning.
6. **Cutover decision** — a new accepted governance ADR names the authority
   provider, root principal/authentication boundary, exact cutover snapshot,
   backup/rollback points and operational recovery procedure.
7. **Promotion** — only the governed cutover operation moves the canonical head.
   Git changes role to an audit/export mirror only if the cutover ADR explicitly
   says so.

Cutover acceptance requires zero unresolved semantic divergence, successful
backup/restore, fresh-session Project Continuity, governance/authentication tests,
failure injection around atomic commit and head movement, and a demonstrated
rollback that does not create two active authorities.

### 12. Initial implementation boundary

Implementation is divided into sequential, independently reviewable batches.
Each batch must publish its exact fixtures, expected results and validation
evidence before the next batch is accepted.

| Batch | Deliverable | Acceptance and failure boundary |
| --- | --- | --- |
| K1 | Versioned semantic objects/serialization, in-memory adapter and import of one exact Git snapshot | Golden hash vectors, acyclic digest graph, round-trip raw-source fidelity, lifecycle/provenance preservation and explicit unknown historical authentication; any silent coercion or invented authority fails. Memory is a reference adapter, not durable production authority. |
| K2 | Transaction, authority and idempotency protocol | Race two writers on one base; only one commits. Inject failures before commit and after commit/before acknowledgement; same-key recovery returns one durable result. Reject changed-key payloads, stale bases and self-authorizing governance changes. A restart-capable test adapter proves durable receipts; memory-only tests cannot claim crash recovery. |
| K3 | Resolved views and compatible query/bundle pipeline | Fixed old/new corpus agrees on mandatory inputs, constraints, lifecycle, explicit IDs, budgets, evidence and unknown semantics. Bundles always retain not_granted. Missing inputs, index mismatch and nondeterministic replay are covered by negative fixtures. Unexplained semantic divergence fails. |
| K4 | Canonical export/restore and continuity proof | Stable semantic manifests despite evidence availability changes; separate package digests, omission diagnostics, corruption/missing-object tests, empty-adapter restore and fresh-session continuity. Incomplete required evidence blocks full recovery and authority promotion. |

K1 is the next implementation boundary, not authorization to implement all four
batches at once. This ADR accepts architecture only; regression of existing tools
does not prove an unimplemented kernel. No batch cuts over authority or adds a
daemon, distributed consensus, plugin framework, broad event bus, arbitrary query
language or storage-product commitment. Storage choice follows conformance and
workload evidence; production authority still requires a separate cutover ADR.

## Alternatives Considered

1. **Choose SQL first and let its schema define Context.** Rejected because table
   design would prematurely become the semantic model and make migration,
   provenance and authority behavior database-specific.
2. **Keep Git files as the permanent semantic API.** Rejected as a permanent rule
   because the current representation already makes transactions and retrieval
   expensive; retained as the accepted current authority and a reference adapter.
3. **Make `qiven-context.exe` an always-on authoritative service immediately.**
   Rejected because process lifetime and transport do not establish semantics or
   authority, and current requirements do not yet justify daemon complexity.
4. **Use an append-only event stream as the only source of truth.** Rejected as a
   mandated representation. Immutable transaction ancestry is semantic, but
   event-sourcing mechanics are one possible adapter design.
5. **Allow Git and the engine to be canonical simultaneously during migration.**
   Rejected because unsynchronized dual authority recreates the conflict problem
   Context exists to prevent.
6. **Treat a restored backup as authoritative when checksums pass.** Rejected
   because integrity and authority are different questions.

## Consequences

Context gains a stable semantic center that can survive storage, process and
transport replacement. Transactions become atomic and explainable, snapshots and
exports become portable, and AI consumption can be optimized without making an
index or model authoritative.

The architecture imposes deliberate implementation work: canonical serialization,
typed errors, adapter conformance, transaction validation, import/export tooling,
equivalence tests and a separately governed cutover. Until those proofs exist,
GitHub remote remains canonical and the current tools remain operational.

The kernel must remain stricter than a generic document database. Arbitrary blobs
may be preserved as evidence, but canonical cognition requires registered types,
lifecycle and provenance.

## Revisit Conditions

Revisit the initial single-head optimistic transaction model if real concurrent
authorized writers require branching/merge semantics that can preserve all
invariants. Revisit service/daemon deployment when measured multi-client, latency
or availability needs justify it. Revisit export ancestry retention if project
scale proves full reachable history impractical, but never remove the ability to
explain the accepted snapshot and its lifecycle.

Revisit the storage choice only after kernel conformance and workload measurements
exist. Revisit canonical authority only through the explicit cutover protocol.
