# Owner-invoked session designations carry no model binding

## Context

ADR-0035 requires participant roles to be fulfilled through qualified
model bindings declared in the active ContextView. The
`jason-extended-cognition` designation view originally declared the
provisional binding `jason-extended-cognition-glm5-3-flash`, and every
serving-model difference from that declaration had to be handled as a
substitution disclosure (ADR-0035 rule 4) — producing a standing
"flash-variant not self-verifiable from inside the session" disclosure
in v11/v14/v15 checkpoints without any decision value: the owner
invokes the designation deliberately and already knows which model is
serving.

The 2026-09-22 owner direction removed the binding from the view
(PR #95). This ADR canonicalizes that exception class so a future cold
boot does not read ADR-0035 as requiring a binding for it.

## Decision

1. A session designation that is **explicitly owner-invoked per
   session** (today: `jason-extended-cognition`) carries **no model
   binding** and no binding qualification. The invocation itself is the
   model-selection evidence: the owner knows which model serves the
   session; no record can add decision-relevant information to that
   knowledge.
2. In place of qualification and substitution disclosure, the serving
   LLM performs a **switch-time live-model report**: at designation
   switch (and in the session checkpoint) it reports the live model
   family, variant and reasoning effort **as observable from inside the
   session**; fields that are not introspectable from inside are
   reported as such, never guessed. This preserves attribution
   provenance (commit trailers unchanged) without pretending to a
   binding-based guarantee the session cannot verify.
3. Views for participant combinations that are NOT owner-invoked per
   session (chatgpt-jason, zcode-jason) keep ADR-0035 bindings and the
   rule-4 disclosure duty unchanged. The extended-cognition
   designation's `switch_report` field in its view file is the
   normative record of this exception.

## Alternatives Considered

Keep the binding and continue disclosure (rejected: the disclosure
carried no decision value — the owner's knowledge strictly dominates
it — and the non-introspectable flash variant made the record
permanently approximate); extend the exception to all views (rejected:
ordinary sessions are not individually owner-invoked, so binding
evidence still adds qualification value there); record the exception
only in the view file (rejected — it already was, and the 2026-09-22
audit classed it as drift against ADR-0035; an accepted decision is the
durable carrier).

## Consequences

Cold boots load ADR-0035 and this ADR together: bindings bind ordinary
views; owner-invoked designations report live at switch. A future
designation gets the same exception only through the same channel —
explicit per-session owner invocation recorded in the view. Commit
attribution trailers (`role:` / `LLM:` / reasoning) are unaffected.

## Revisit Conditions

A designation is ever granted through automation or delegation instead
of explicit owner invocation (then a binding or an equivalent
evidence-based gate is required); or the harness begins exposing the
serving variant/reasoning introspectably (then the report becomes
exact and the exception may be revisited for simplification).

## Provenance

2026-09-22 v16 governance session: binding removal (PR #95) followed by
the full-audit finding that the exception lived only in view material
and current.md, competing with ADR-0035's requirement.
