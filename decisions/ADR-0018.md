# Delay repository splits and workspace orchestration until coordination or reuse is real

## Context
Qiven has many plausible future shared libraries and product repositories. Creating them early would make architecture look organized while increasing versioning, CI, dependency, release, and coordination cost before the underlying boundaries are proven.

## Decision
Create a new shared repository only when there is a stable ownership boundary, meaningful independent lifecycle, or demonstrated reuse that justifies the coordination cost. Product verticals should remain comparatively coarse-grained until real pressure requires a split.

`qiven-workspace` is a future composition/orchestration layer, not a repository that should exist merely because multiple repositories are imaginable. Introduce it when multi-native-repository version composition, coordinated validation, or workspace orchestration becomes a concrete recurring problem.

Candidate future repositories and names are planning vocabulary, not implementation commitments.

## Alternatives Considered
Creating the full projected repository graph up front; using one giant monorepo for all native and business products; creating qiven-workspace immediately as a ceremonial top-level repository.

## Consequences
The current repository count stays small and each split must earn its operational cost. Some future extraction work may be required once boundaries become clear, but that cost is preferred over maintaining speculative repositories and dependency edges.

## Revisit Conditions
Revisit when two or more real consumers need an independently versioned shared component, or when multi-repository composition and validation repeatedly create manual coordination burden.

Genesis reconstruction from accepted ecosystem discussions. The current Devkit README independently preserves the same staging idea by describing qiven-workspace as a possible future owner of ecosystem composition that does not yet exist.
