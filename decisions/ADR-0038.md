# Place Runtime Cognitive Control at harness-observed boundaries and require complete mediation for governed actions

## Context

The v4 cognition-activation architecture is frozen.

Its final executable semantic baseline is:

```text
JasonHuang3D/qiven-context-draft
4cbc99549c70ef1caa5ccfd6bc15f95607b10322
```

The final freeze establishes, among other things:

```text
ActionIntent
InvocationPolicy
CognitiveRequirement
CognitiveNeed
PreparationPacket

RequirementBoundary:
    BeforeJudgment
    BeforeExecution

RequirementStatus:
    Pending
    Satisfied
    Failed

ready_for_judgment()
ready_for_execution()
```

and the following hard semantic principles:

```text
No consequential action may rely on latent recall alone.

A known pit requires an invocation path.

Listed requirements are not satisfied requirements.

Mandatory control obligations originate from policy,
not from participant confidence.

CognitiveNeed is discretionary.

Canonical and live claims require their authoritative evidence classes.

Blind retry without new evidence is not recovery.

The hidden interior of reasoning remains opaque.
```

v4 deliberately does **not** specify how these semantics attach to a real LLM runtime.

That becomes the first Runtime ADL problem.

The naive runtime interpretation would be:

```text
LLM
    ↓
remembers that Cognitive Control exists
    ↓
constructs ActionIntent
    ↓
calls Qiven
    ↓
Qiven prepares context
```

This architecture is invalid.

It recreates the exact failure class v4 exists to eliminate:

```text
the project knows a control rule
    ↓
the participant must remember to invoke it
    ↓
participant forgets
    ↓
control never runs
```

The control plane cannot depend on the controlled participant voluntarily invoking it.

Modern agent harnesses expose a stronger physical boundary.

An LLM generally cannot directly mutate a filesystem, execute Git, invoke a compiler, publish a repository, or call an MCP server.

It emits a structured request.

A host or harness receives that request and decides whether and how the corresponding mechanism executes.

Conceptually:

```text
LLM output
    ↓
structured tool/action request
    ↓
HARNESS
    ↓
tool executor
    ↓
world
```

That boundary already exists independently of Qiven.

For mechanism-level actions, the structured request is already a machine-readable expression of proposed action.

For example:

```text
Write {
    path: "include/qiven/foo.hpp",
    content: ...
}
```

is sufficient to know, mechanically:

```text
a file write is being proposed

target:
    include/qiven/foo.hpp
```

The LLM does not need to separately remember to announce:

```text
"I intend to write include/qiven/foo.hpp."
```

before the runtime can control that operation.

Real harnesses provide corresponding interception surfaces.

ZCode, for example, exposes lifecycle/tool boundaries conceptually matching:

```text
SessionStart
UserPromptSubmit

PreToolUse

PermissionRequest

PostToolUse
PostToolUseFailure

Stop
```

This demonstrates that the physical topology required by v4 exists in a practical desktop agent runtime.

However, ZCode is only one harness.

Qiven must remain independent of:

```text
ZCode
ChatGPT
Codex
Claude
GLM
MCP
a specific tool schema
a specific hook API
```

Therefore the Runtime architecture needs an abstraction one level above any individual hook system.

The key design question is:

> Where must Cognitive Control physically sit so that mandatory activation and enforcement do not depend on model cooperation?

---

## Decision

### 1. Cognitive Control is external to Judgment

The production Cognitive Control plane MUST live outside the reasoning participant whose actions it governs.

A participant may be:

```text
LLM
human
future reasoning model
other judgment engine
```

but none of those participants is the authoritative executor of mandatory invocation policy.

The fundamental topology is:

```text
Judgment
    ↓
proposal
    ↓
Runtime Boundary
    ↓
Cognitive Control
    ↓
Mechanism
```

not:

```text
Judgment
    ↓
optional self-invocation of Cognitive Control
    ↓
Mechanism
```

Therefore:

> **Judgment proposes.
> The runtime observes.
> Cognitive Control decides what is required.
> Mechanism executes only after the governed boundary permits it.**

This externalization is mechanically enforceable only for paths inside
a deployment profile's declared **governed actor set** and capability
universe (the DeploymentProfile of Section 8).

A human participant acting directly — for example the project owner
executing in a foreground terminal — is not an architectural exemption
from Qiven semantics. It is a mediation-scope question:

- if that direct-human path is included in the deployment profile's
  governed actor set and capability universe, then it is an
  **unmediated execution path**; operation classes reachable through it
  are `not fully governed` by Runtime interception and hard-enforcement
  claims are bounded accordingly;

- if the profile governs only a machine participant and explicitly
  excludes owner-manual execution from its governed actor set, then the
  profile's hard-enforcement claim is scoped to that actor set and MUST
  NOT be generalized to the excluded human path.

Governance of direct human execution remains supplied by the
collaboration contracts — typed human handoffs (H1-H4) and the owner's
execution authority. A human acting through a mediated harness or
execution surface may be governed by the same Runtime Cognitive Control
plane as any other participant.

---

### 2. The harness boundary is the primary physical enforcement point

Qiven Runtime MUST integrate with the point at which proposed external actions cross from model output into executable mechanisms.

The architecture names this abstract boundary:

```text
Action Interception Boundary
```

Its implementation is harness-specific.

Examples may include:

```text
ZCode PreToolUse

an MCP proxy

a Codex tool dispatcher interceptor

a local execution broker

a CLI execution wrapper

a future ChatGPT connector/tool boundary
```

The architecture does **not** require Qiven to own or reimplement every underlying tool.

It requires Qiven to be able to mediate consequential actions before those tools execute.

---

### 3. Tool calls are observable action proposals, not trusted semantic truth

A structured tool request is treated as an observable proposal.

For example:

```text
tool = Write
path = include/qiven/foo.hpp
```

provides trusted mechanism-level facts about the requested operation:

```text
operation class:
    file mutation

target:
    include/qiven/foo.hpp
```

It does **not** automatically prove higher-level semantic intent such as:

```text
IntroducePrimitive

ModifyArchitecture

ModifyPublicAPI

FixBug

Refactor
```

Therefore production Runtime distinguishes:

```text
ObservedAction
```

from:

```text
ActionIntent
```

Conceptually:

```cpp
struct ObservedAction
{
    HarnessId harness;
    ToolId tool;
    OperationId operation;

    ResourceTarget target;
    StructuredArguments arguments;
};
```

and:

```cpp
struct ActionIntent
{
    ActionKind kind;
    ClaimClass claimClass;

    ...
};
```

`ObservedAction` describes what the harness can prove is being requested.

`ActionIntent` describes the semantic control classification required by frozen v4.

---

### 4. ActionIntent may have multiple evidence sources

Production `ActionIntent` MUST NOT depend exclusively on model self-declaration.

Its classification may combine:

```text
A. mechanism observation
   tool name
   operation
   target
   arguments

B. deterministic structural analysis
   modified path
   public-header detection
   diff shape
   symbol creation
   Git operation
   publication operation

C. explicit semantic declaration
   participant-declared intent
   workflow metadata
   optional declare_intent protocol

D. semantic analysis
   model/classifier assistance when deterministic classification is insufficient
```

These sources have different authority.

Mechanically observable facts are authoritative for what they actually establish.

Participant declarations are proposals.

They may enrich classification.

They MUST NOT be allowed to downgrade a mechanically observed control requirement.

Source D follows the classifier rule of Section 19: a semantic
classification is a Judgment output, not a mechanical proof, and a
deployment profile whose enforcement claim relies on semantic-only
intent classification defines the accepted classifier, its uncertainty
behavior and the scope of the claim.

Example:

```text
ObservedAction:
    git push

Participant says:
    "this is only local experimentation"
```

must still classify through the publication policy appropriate to the actual operation.

Likewise:

```text
ObservedAction:
    Write public header
```

cannot be downgraded solely because the thinker failed to declare:

```text
ModifyPublicAPI
```

---

### 5. Optional semantic intent declaration is permitted but is never the enforcement root

A harness adapter MAY expose an explicit semantic-intent mechanism such as:

```text
declare_intent(
    action = IntroducePrimitive,
    concept = "hashing",
    rationale = "...",
    expectedEvidence = [...]
)
```

This can improve latency and reasoning quality.

For example, early declaration allows Cognitive Control to retrieve lower-layer implementations **before** the model has already drafted the new implementation.

However:

```text
declare_intent
```

is advisory/propositional.

The correctness of mandatory control MUST NOT depend on the LLM remembering to call it.

If no semantic intent was declared and a later observable action crosses a governed boundary:

```text
PreToolUse / equivalent interception
```

must still execute Cognitive Control.

Therefore:

> **Semantic declaration may reduce friction.
> It may never be required for enforcement correctness.**

---

### 6. Runtime introduces an abstract Action Interception Port

The production architecture defines a harness-independent port.

The exact interface is deferred to detailed design, but its semantic contract is:

```cpp
class IActionInterceptionPort
{
public:
    virtual ObservedAction observe_proposal(...) = 0;

    virtual void allow(...) = 0;
    virtual void deny(...) = 0;

    virtual void return_context(...) = 0;
};
```

This is not the final API.

Its architectural responsibility is fixed:

```text
capture externally meaningful proposal
before mechanism execution

deliver proposal to Cognitive Control

prevent execution when Cognitive Control refuses

return control information to Judgment when re-deliberation is required
```

Adapters implement this contract for specific harnesses.

---

### 7. Boundary triggers and requirement deadlines are orthogonal axes

v4 freezes two requirement **deadline** values:

```text
RequirementBoundary:
    BeforeJudgment
    BeforeExecution
```

The runtime contributes physical **triggers**:

```text
activation trigger:
    session start, prompt submission, task transition

action trigger:
    pre-execution interception of a proposed action

claim trigger:
    outbound claim boundary
```

These are two orthogonal axes, not a one-to-one mapping:

- the deadline axis is semantic and frozen: by which governed
  continuation point a requirement must already be satisfied;

- the trigger axis is physical and harness-specific: where the runtime
  obtains enough observable information to derive, check or resolve the
  requirement.

A crucial consequence follows from the frozen v4 control shape:
`ActionIntent` is itself a **proposal** emitted by Judgment. It may be the
first point at which the runtime can know that a rule such as
`SearchLowerLayer`, `InspectKnownPit`, or `VerifyCanonical` applies.
Therefore a `BeforeJudgment` requirement discovered at an action or
claim trigger is not satisfied retroactively and the proposal is not
treated as an accepted/authoritative judgment. Instead:

```text
Judgment produces provisional proposal
    ↓
action / claim trigger observes it
    ↓
Cognitive Control derives BeforeJudgment requirement
    ↓
requirement unsatisfied
    ↓
withhold / deny current proposal
    ↓
resolve and return required cognition
    ↓
new Judgment cycle
```

The **new** Judgment cycle is the one permitted to continue with that
intent, and it runs only after the `BeforeJudgment` requirement is
satisfied.

Accordingly, correctness is expressed as two semantic gates rather than
as "every physical trigger must occur before the first model thought":

```text
JudgmentContinuationAllowed(intent)
    iff every blocking BeforeJudgment requirement for that intent
        is Satisfied

ExecutionAllowed(action)
    iff JudgmentContinuationAllowed(intent)
       and every blocking BeforeExecution requirement
           is Satisfied
```

These gates are the runtime reading of v4's frozen
`ready_for_judgment()` / `ready_for_execution()` and inherit their
full contract: a preparation failure — for example a missing policy
materialization — fails both gates regardless of the derived
requirement set, exactly as v4's `PreparationFailure` handling
specifies.

Activation triggers are valuable because they can satisfy predictable
requirements early and avoid denial/re-deliberation loops. Action and
claim triggers are authoritative late-discovery points for requirements
that become knowable only after a proposal exists. They may force
re-deliberation, but they may never waive the frozen deadline.

A deployment profile has full v4 boundary coverage only if its trigger
set guarantees both semantic gates for every governed path: an intent
cannot continue as prepared judgment with an unsatisfied
`BeforeJudgment` requirement, and a mechanism cannot execute with an
unsatisfied `BeforeExecution` requirement.

### 8. Complete mediation is required for any action Qiven claims to govern

A control policy has no enforcement meaning if the controlled action can bypass it.

Therefore:

> **Any action class for which Qiven claims mandatory enforcement MUST be completely mediated by an accepted interception path.**

For a governed runtime profile, this is invalid:

```text
LLM
 ├── Qiven-controlled Write
 ├── Qiven-controlled Git
 └── unrestricted raw shell
         ↓
      same filesystem / Git repository
```

because the raw shell provides an equivalent unmediated mutation path.

The architecture therefore distinguishes:

```text
available capability
```

from:

```text
governed capability
```

through a declared **deployment profile** containing three coupled
parts:

```text
GovernedActorSet
CapabilityUniverse
MediationInventory
```

`GovernedActorSet` names the participant/principal classes to which the
profile's Runtime enforcement claim applies.

`CapabilityUniverse` enumerates the execution capabilities exposed to
that governed actor set by the deployment — tools, transports, direct
execution paths and other channels capable of reaching governed
operation classes. It is **not** an assertion about every capability
physically present on the host.

`MediationInventory` declares which capabilities in that universe are
mediated by accepted interception paths.

Hard-enforcement claims are therefore always qualified by:

```text
(DeploymentProfile, GovernedActorSet, OperationClass)
```

and derive from the declarations together:

- an operation class whose every producing capability reachable by the
  governed actor set in the declared universe is mediated may claim
  hard enforcement, subject to conformance proof of those paths;

- an operation class with any unmediated producing capability reachable
  by the governed actor set in the declared universe MUST be reported as
  `not fully governed`, and hard enforcement MUST NOT be claimed for it.

A bypass is thereby well-defined: another capability inside the same
declared actor-scoped universe reaches the same operation class without
accepted mediation.

The reporting duty is actor-scoped as well: a profile that excludes
an actor class able to reach governed operation classes MUST surface
that exclusion explicitly in its governance report, with the same
honesty as a `not fully governed` operation class.

This is a fail-closed property of deployment configuration, not a
conversational assumption — and not a runtime claim that Qiven can
discover every executable path on a machine. The runtime does not
attempt to discover unknown bypass paths; conformance verifies that the
declared actor set and capability universe are complete for the profile
being claimed, and Runtime refuses enforcement claims the accepted
profile/inventory cannot support.

The accepted profile is versioned content. If exposed capabilities,
actor reachability, adapter wiring or mediation coverage changes, the
previous conformance claim becomes stale until the new profile revision
is validated. An `ALLOW` decision is therefore bound to the accepted
profile revision as specified in Section 14.

Scenario R6 and property HA-7 test this declarative semantics.

### 9. Cognitive Control and the Host execution-authority plane are conjunctive orthogonal gates

ADR-0026 establishes `qiven-host` as the JasonPC-resident authority
boundary for production local execution: admission, the single-writer
lease, monotonic fencing epochs, quarantine, reconciliation, and the
bounded execution journal.

That plane remains in force. This ADR does not place Cognitive
Control above or below it: the two are **conjunctive orthogonal
gates** over the same governed local action, and both must allow.

```text
Cognitive Control gate:
    "do the required cognitive conditions hold
     for this exact action?"

Host execution-authority gate:
    "is this execution admitted under the machine-local
     single-writer / fencing / no-bypass authority?"

governed local action requires:
    Cognitive Control ALLOW   AND   Host broker admission
```

Neither gate can substitute for the other: a cognitively satisfied
action is not thereby execution-admitted, and an execution-admitted
action is not thereby cognitively satisfied.

On JasonPC, an interception adapter whose governed actions include
machine-local mutation MUST route that mutation through the accepted
host-authority path — or remain non-mutating — exactly as the current
fail-closed DCR suspension and Workflow 2 rules already require. An
adapter that executes local mutation around the broker reproduces the
2026-09-16 split-brain failure class at a new layer and is a safety
defect.

Where no Host broker is accepted for a deployment (for example a
non-JasonPC harness), the adapter composes conjunctively with
whatever execution-authority mechanism that deployment accepts, and
the profile's governance claims are bounded by that composition.

### 10. Cognitive Control operates as a pre-boundary decision loop

For a proposed governed action:

```text
ObservedAction
    ↓
Intent Classification
    ↓
ActionIntent
    ↓
InvocationPolicy
    ↓
PreparedRequirements
```

Cognitive Control then attempts to satisfy requirements whose mechanisms are available.

Conceptually:

```text
Proposal
    ↓
Observe
    ↓
Classify
    ↓
DeriveRequirements
    ↓
Resolve
    ↓
PreparationPacket
```

Then:

```text
ready_for_judgment == false
    ↓
do not execute
    ↓
return missing cognition/evidence
    ↓
Judgment deliberates again
```

or:

```text
ready_for_judgment == true
    ↓
Judgment may complete/revise the proposed action
```

and before world mutation:

```text
ready_for_execution == true
    ↓
ALLOW
    ↓
Mechanism
```

Otherwise:

```text
DENY / DEFER / ASK
```

depending on requirement and policy.

---

### 11. DENY is a control-flow transition, not an exceptional failure

A denied action does not necessarily mean:

```text
the task failed
```

It often means:

```text
the proposal crossed a boundary
before required cognition was active
```

Example:

```text
LLM proposes Write:
    new hashing utility

Control recognizes:
    possible IntroducePrimitive

Required:
    SearchLowerLayer

No search evidence exists
```

Correct behavior:

```text
DENY execution

resolve/search lower layer

return:
    qiven::fnv1a64
    qiven::fnv1a64_chain
    ...

Judgment resumes

model may now:
    reuse
    extend
    wrap
    or justify a new primitive
```

Thus control denial is part of normal reasoning orchestration.

It is not necessarily an error or a human escalation.

### 12. Preparation may return cognition to Judgment before execution

The production control plane MUST have a path for bringing satisfied cognition/evidence back into the participant's effective reasoning context.

This is the runtime realization of:

```text
PreparationPacket
```

The physical method is adapter-specific.

Examples may include:

```text
hook additionalContext

new model turn

tool result carrying preparation

MCP response

structured agent-runtime message
```

The architecture requires the effect:

```text
required cognition becomes part of the next Judgment input
```

not a specific transport primitive.

This is the causal property v4 is designed to guarantee.

---

### 13. Requirement satisfaction is production-trusted state

The draft helper:

```cpp
mark_satisfied(...)
```

is reference-only.

Production Runtime MUST NOT permit arbitrary participants to mark mandatory requirements satisfied.

Requirement satisfaction must originate from the mechanism authorized to resolve that requirement class.

Examples:

```text
MandatoryRecall
    ← cognition resolver

SearchLowerLayer
    ← lower-layer search mechanism

VerifyCanonical
    ← canonical cognition resolver

VerifyLive
    ← live-source verifier

InspectToolContract
    ← tool registry

InspectKnownPit
    ← failure/pit resolver

RunMechanicalCheck
    ← actual gate/check execution

RequestReview
    ← accepted review evidence

AskHuman
    ← typed human handoff evidence
```

Therefore:

> **Judgment can request evidence.
> Judgment cannot mint the evidence that proves its own mandatory requirement satisfied.**

The registry that authorizes resolvers for requirement classes is
itself part of the trusted base: a resolver that marks requirements
satisfied without performing its mechanism would silently break
fail-closed semantics. How resolvers are accepted, versioned and
bound to requirement classes is a mandatory component-ADL question
(see Follow-on Design Boundary).

---

### 14. Authorization is logical, not yet bound to a physical token type

Once all required pre-execution conditions are satisfied, Cognitive Control produces a logical:

```text
ALLOW
```

for the exact proposed action.

This ADR does **not** require a specific physical representation such as:

```text
PreparedActionPermit
opaque capability token
signed receipt
hook return object
```

Different harness adapters may implement authorization differently.

For example:

```text
ZCode:
    PreToolUse returns allow

future broker:
    opaque action permit

in-process runtime:
    direct function decision
```

The invariant is:

> The mechanism executes only after the exact proposal has passed the required Cognitive Control boundary.

`ALLOW` is **non-transferable and non-replayable as a semantic decision**.
Even when an adapter represents it only as an immediate hook return, the
decision is bound to the control facts that produced it:

```text
exact observed proposal / action identity
classified ActionIntent
pinned cognition revision and materialized InvocationPolicy
blocking requirement set
trusted evidence that satisfied those requirements
accepted DeploymentProfile revision
```

`pinned` means decision-time cognition reads are bound to exactly one
immutable Snapshot revision for the decision's lifetime. The staleness
rule below is deliberately strict — any advance of that revision stales
the decision; narrowing staleness to material changes is a
component-ADL optimization that must preserve this binding contract.

If any bound fact changes before execution — for example the tool arguments
are rewritten, the target path changes, the pinned cognition/policy revision
advances, required evidence is superseded, or the deployment profile changes
— the previous `ALLOW` is stale and the action MUST re-enter Cognitive
Control. This is the semantic anti-TOCTOU rule; the physical representation
of the binding is deferred, not the binding itself.

Host execution authority remains orthogonal: a Cognitive Control `ALLOW`
does not mint or extend a Host lease/fencing epoch, and the Host admission
used at execution must independently be current.

Detailed design will determine whether an explicit capability object is
required for particular adapters.

---

### 15. Post-execution observation is a separate runtime boundary

Pre-execution control alone is insufficient.

The runtime MUST also observe results.

Conceptually:

```text
Mechanism
    ↓
PostActionObservation
```

The observation records at least:

```text
outcome:
    Succeeded
    Failed
    Indeterminate

tool / operation

target

stable result identity where applicable

evidence produced

failure information where a failure is known

uncertainty / reconciliation evidence where completion is unknown
```

`Indeterminate` is first-class. Transport loss, timeout, hook failure,
process disappearance, lost acknowledgement, or partial observation can
leave the runtime unable to prove whether a side effect occurred. Absence of
a success receipt is not proof of failure, and a mechanism-level failure is
not proof of "no side effect" unless that mechanism contract explicitly
guarantees failure atomicity.

This supports:

```text
EvidenceRecord generation

FailureFingerprint generation for known failures

retry discipline

reconciliation for unknown outcomes

live-state refresh

future cognition transaction proposals
```

### 16. Failure and indeterminate outcomes feed different next-control paths

A material **known failure** must causally affect subsequent behavior.

The known-failure path is:

```text
Action
    ↓
Mechanism
    ↓
Known Failure
    ↓
FailureFingerprint
    ↓
runtime state / evidence
    ↓
next RetryFailure intent
    ↓
InspectKnownPit
    ↓
blind-retry gate
```

Therefore the participant does not need to remember:

> "I failed this exact thing before, perhaps I should search the pit ledger."

The harness/runtime already observed the known failure. The next equivalent
operation can be intercepted mechanically.

An **indeterminate outcome** is different and MUST NOT be normalized into a
failure merely to keep the loop moving:

```text
Action
    ↓
Mechanism
    ↓
Outcome unknown
    ↓
reconciliation-required runtime state
    ↓
equivalent / conflicting mutation blocked
    ↓
authoritative observation or Host reconciliation
    ↓
resolved as Succeeded / Failed
        or remains unresolved
```

Until reconciliation resolves the effect, Runtime MUST NOT:

```text
mint a FailureFingerprint that asserts the action failed
treat absence of evidence as evidence of no mutation
permit an equivalent blind retry
publish a success/failure claim it cannot prove
```

If reconciliation resolves the action as failed, the normal
`FailureFingerprint -> InspectKnownPit -> retry discipline` path begins. If it
resolves as succeeded, success evidence is recorded. If it remains
unresolved, the conflicting operation class remains fail-closed according to
the deployment's recovery policy.

This aligns Cognitive Control with the Host authority model's existing
`reconciling` semantics: uncertainty about completion is a distinct world,
not a synonym for failure.

Together these paths realize v4's known-failure discipline without
modeling hidden reasoning:

```text
Known failure
→ Learn/Recall (InspectKnownPit)
→ Retry Control
```

The unknown-outcome path is **this ADR's extension**, aligned with the
Host authority model's `reconciling` state (ADR-0026), not a
v4-frozen rule:

```text
Unknown outcome
→ Reconcile
→ then classify the next legal transition
```

### 17. Cognitive runtime state and canonical cognition remain distinct

The Runtime Control Plane will need short-lived state such as:

```text
observed proposals in flight
(one keyed stream per intercepted session/agent/tool-call)

prepared requirements

tool execution correlation

recent FailureFingerprint

pending action classification

adapter session identity

temporary evidence
```

This state is not automatically canonical cognition.

The architecture preserves:

```text
runtime control state
≠
Snapshot
```

A material lesson, accepted decision, obligation, pit, policy change, or durable evidence enters canonical cognition only through the existing governed cognition transaction path.

Runtime state may therefore emit a **cognition transaction proposal**; it
does not write canonical cognition directly. Acceptance, authority,
provenance and persistence remain owned by the canonical cognition path.

This prevents the control runtime from becoming a hidden second cognition store.

Two structural rules follow.

**Policy is read, never minted.** InvocationPolicy is canonical
**materialized policy inside the Snapshot**: v4 freezes it as
cognition data carried as a Snapshot member, and the runtime reads
the policy materialized in the canonical Snapshot through the
CanonicalCognitionPort. Natural-language records and constraint
declarations do not reach the runtime as policy directly; they
change the materialized policy only through the governed cognition
transaction path (including the ADR-0036 operation classes, which
this runtime mechanizes). The runtime MUST NOT become a second
policy store: local caching is a derived view of the Snapshot's
policy materialization, never an independent derivation from prose,
and a missing policy materialization fails closed exactly as v4
specifies.

**Concurrent proposals are first-class.** Real harnesses run parallel
tool calls and subagent fan-out; there is no single "current
proposal". Runtime control state is keyed by the correlation
identity of each intercepted stream (session, agent, tool-call), and
every correlation rule must remain correct with several streams in
flight. The exact keying and isolation model is a mandatory
component-ADL question (see Follow-on Design Boundary).

---

### 18. Tool boundaries are not sufficient for every v4 ActionKind

Some v4 actions map naturally onto tool execution:

```text
InvokeTool
Commit
Publish
RetryFailure
file mutation
```

Others may occur without a tool request:

```text
MakeCanonicalClaim
MakeLiveClaim
AcceptCandidate
some architecture judgments
```

For this reason Runtime ADL recognizes a second abstract boundary:

```text
Outbound Claim Boundary
```

A harness adapter SHOULD expose the point before a governed response or claim leaves the reasoning runtime.

Examples include:

```text
agent Stop

final answer emission

review verdict submission

candidate acceptance

commit-message or PR-description publication
```

This boundary enables Cognitive Control to enforce requirements such as:

```text
VerifyCanonical
VerifyLive
RequestReview
```

even when no ordinary tool request generated the claim.

Two claim channels must be distinguished:

```text
claims embedded in tool arguments
    commit messages, PR descriptions, review verdicts
    submitted through tools
    -> already cross the action boundary;
       intercepted there as ordinary governed actions

claims in free response text
    the assistant reply itself
    -> cross only the outbound claim boundary
```

The first runtime landing governs the **tool-mediated** channel.
Free-text claim governance is a later profile: it inherits the
uncertainty semantics of the next section and MUST NOT silently
degrade the performance rule that keeps interception
boundary-triggered.

---

### 19. Claim interception and claim classification are separate problems

The runtime can usually guarantee that an outbound response passes through an output boundary.

It may not always be able to mechanically determine:

```text
whether arbitrary natural-language output contains
a canonical or live factual claim
```

Therefore:

```text
interception reliability
```

and:

```text
semantic classification reliability
```

must remain separate.

Where claim classification is mechanically specification-closed, use deterministic mechanisms.

Where semantic judgment is required, an analyzer or reasoning participant may propose a classification.

Such a semantic classification is itself a **Judgment output**, not a
mechanical proof. It may select which policy branch to evaluate, but it does
not by itself satisfy a mandatory requirement. A deployment profile whose
hard-enforcement claim depends on semantic-only classification MUST define
the accepted classifier, its uncertainty behavior and the scope of the claim;
it may not advertise a stronger guarantee than that classifier contract
supports.

If classification is uncertain at a policy-defined blocking boundary, the runtime must surface uncertainty rather than silently treating it as:

```text
no requirement
```

This preserves the v4 fail-closed distinction.

For the first tool-mediated landing, deterministic structural classification
SHOULD be preferred wherever the tool/target/diff shape is specification-closed.
Free-text semantic classification remains a later profile.

The detailed classification strategy is deferred.

---

### 20. Harness adapters are replaceable Mechanisms

The production architecture therefore has the following logical shape:

```text
                    Human / LLM / Thinker
                            │
                            │ proposal
                            ▼
                     Harness / Host
                            │
                  ┌─────────┴─────────┐
                  │                   │
            Action Boundary      Claim Boundary
                  │                   │
                  └─────────┬─────────┘
                            ▼
                  Interception Adapter
                            │
                            ▼
                    Intent Classifier
                            │
                            ▼
Canonical Cognition ─────► Cognitive Control
(pinned Snapshot)          │
      │                    │
      └─ InvocationPolicy  │
         + durable         ▼
           cognition    Requirements
                            │
                            ▼
                  Requirement Resolvers
                            │
                            ▼
                   PreparationPacket
                      ┌─────┴─────┐
                      │           │
                    DENY        ALLOW
                      │           │
          return cognition        │
          / re-deliberate         ▼
                              Mechanism
                                  │
                                  ▼
                         PostActionObservation
                                  │
                     ┌────────────┴────────────┐
                     │                         │
                  Evidence              Failure / Unknown
                     │                         │
                     └────────────┬────────────┘
                                  ▼
                           RuntimeControlState
                                  │
                                  │ governed cognition
                                  │ transaction proposal
                                  ▼
                       Canonical cognition path
                       (authority / acceptance /
                        persistence / provenance)
                                  │
                                  ▼
                         Canonical Cognition
```

Two causality rules are normative:

1. **Canonical cognition is an upstream authority input.** Cognitive Control
   reads a pinned Snapshot and its materialized `InvocationPolicy`; Runtime
   does not synthesize policy from local state.

2. **Runtime state is not a canonical writer.** Evidence, pits, lessons or
   policy amendments discovered during execution may become governed cognition
   transaction proposals, but only the canonical cognition transaction path
   can accept and persist them.

This is the root Runtime ADL topology.

### 21. ZCode is the first concrete adapter candidate, not part of the architecture contract

The currently observed ZCode harness provides a useful initial mapping:

| Runtime ADL concept            | Candidate ZCode realization             |
| ------------------------------ | --------------------------------------- |
| Session activation boundary    | `SessionStart`                          |
| prompt activation boundary     | `UserPromptSubmit`                      |
| pre-action interception        | `PreToolUse`                            |
| human permission transition    | `PermissionRequest`                     |
| successful observation         | `PostToolUse`                           |
| failure observation            | `PostToolUseFailure`                    |
| outbound response boundary     | `Stop`                                  |
| return preparation to Judgment | `additionalContext` / next-turn context |
| external mechanism             | Write / Edit / Bash / MCP tools         |

This mapping is evidence that the architecture is physically realizable.

It is **not** normative.

The hook vocabulary itself is candidate evidence from the owner's
harness analysis, not a verified interface. The first adapter's
conformance proof must establish the actual surface — in particular
whether a deny carries feedback back into the next judgment cycle
(HA-3/HA-4), and whether the permission transition is a distinct
observable hook. A vocabulary mismatch changes adapter work, not the
architecture.

Qiven Runtime interfaces MUST NOT expose ZCode-specific event names in core architecture types.

A future adapter must be able to provide equivalent semantics without pretending to be ZCode.

---

### 22. MCP is a capability surface, not the mandatory-control root

MCP may expose:

```text
retrieval

canonical cognition access

lower-layer search

tool registry operations

semantic intent declaration

review or evidence operations
```

but registering an MCP tool only makes an action **available** to the model.

It does not guarantee the model will call it.

Therefore:

```text
MCP
=
Mechanism / capability interface
```

not:

```text
mandatory Cognitive Control
```

A mandatory rule may cause Cognitive Control to call or require an MCP-backed resolver.

But mandatory invocation remains a runtime policy responsibility.

---

### 23. Qiven does not require exclusive ownership of the executor

The architecture rejects the requirement:

```text
Every world-changing operation must be implemented
as a Qiven-owned replacement tool.
```

That would create unnecessary wrappers and tight coupling.

Instead:

```text
existing executor
+
complete interception
```

is sufficient when the interception semantics are trustworthy.

For example:

```text
existing Write tool
+
mandatory pre-execution hook
+
reliable deny semantics
```

can satisfy the architecture.

The key property is:

```text
Qiven can prevent the governed action
from crossing the boundary
```

not:

```text
Qiven wrote the filesystem implementation.
```

---

### 24. The Runtime Control Plane must remain participant-independent

A participant replacement:

```text
GPT
→ GLM
→ Claude
→ future model
→ human
```

must not change:

```text
InvocationPolicy

mandatory requirement derivation

requirement trust source

complete-mediation requirements

external execution boundary semantics
```

Different participants may produce different judgments.

They do not receive different rights to silently bypass the control plane.

This preserves the frozen v4 model-replacement invariant.

---

### 25. The Runtime Control Plane must remain harness-independent at its core

Likewise:

```text
ZCode
→ Codex
→ ChatGPT-compatible harness
→ future custom Qiven host
```

may change:

```text
adapter implementation

event vocabulary

IPC

tool schemas

context-injection mechanism
```

but must not change the core control semantics.

Thus:

```text
Harness Adapter
```

belongs below:

```text
Cognitive Control
```

not inside its policy model.

---

### 26. Process topology is deliberately undecided

This ADR does not decide whether Cognitive Control runs:

```text
inside the harness adapter process

inside a reusable native library

inside qiven-contextd.exe

behind Windows Named Pipes

behind local RPC

inside an MCP server
```

These are deployment/process decisions.

The semantic topology remains the same.

The next ADL/detail-design stage must choose a topology that preserves:

```text
complete mediation

trusted requirement satisfaction

single canonical cognition authority

participant replacement

harness replacement

bounded local overhead
```

without introducing needless distribution.

---

### 27. Canonical storage cutover is deliberately undecided

This ADR does not authorize:

```text
files-as-truth
→
Snapshot-as-truth
```

cutover.

Current canonical `qiven-context` remains authoritative until a separate cutover design and acceptance path exists.

The Runtime may initially operate against existing canonical sources while validating the control topology.

This prevents:

```text
control-plane landing
```

and:

```text
canonical storage migration
```

from becoming one inseparable high-risk change.

---

### 28. K5 transport compression is orthogonal to control topology

`OBL-20260917T192300Z-A7C4E2` (K5 lossless token-efficient LLM
transport) remains open; canonical state defers its sequencing to the
Runtime ADL plan.

This ADR fixes the relationship: K5 changes how canonical cognition
is **encoded for delivery** to a consumer. It does not change where
Cognitive Control sits or what it may enforce. A K5 codec composes
with this architecture as a transport/representation detail behind
the canonical-cognition delivery side of `CanonicalCognitionPort`.

K5 does **not** alter `LiveFactPort` semantics: live verification
remains a separate authoritative-source mechanism whose evidence may
be prepared for Judgment but is not part of the canonical-context
compression contract.

The first runtime landing does not depend on K5, and K5 does not
gate the control-topology proof.

### 29. First Runtime landing should prove control before authority migration

The preferred landing sequence implied by this ADR is:

```text
Frozen v4 semantic contract
        ↓
Harness interception adapter
        ↓
Cognitive Control runtime
        ↓
real requirement resolver(s)
        ↓
allow / deny / re-deliberate loop
        ↓
post-action observation
        ↓
failure/retry proof
        ↓
multi-harness boundary proof
        ↓
only later:
canonical authority/storage cutover
```

The first runtime proof therefore does **not** need to replace `qiven-context`.

It needs to prove:

> The frozen v4 Cognitive Control semantics can causally govern a real LLM/tool loop.

### 30. Minimum first-runtime scenarios

Before storage cutover or broader automation, the runtime must prove at least these scenarios against a real harness.

#### Scenario R1 — tool contract

```text
LLM proposes tool execution
    ↓
interception occurs without LLM explicitly calling Qiven
    ↓
InspectToolContract required
    ↓
missing/invalid contract blocks execution
    ↓
valid contract allows exact invocation
```

---

#### Scenario R2 — lower-layer reuse

```text
LLM proposes code mutation introducing reusable primitive
    ↓
boundary recognizes/enforces SearchLowerLayer
    ↓
without search evidence:
    mutation blocked
    ↓
search result returned to Judgment
    ↓
model re-deliberates
```

Correctness cannot depend on prior:

```text
declare_intent
```

---

#### Scenario R3 — blind retry

```text
tool execution fails
    ↓
PostActionObservation creates FailureFingerprint
    ↓
equivalent retry proposed
    ↓
InspectKnownPit fires
    ↓
no new evidence:
    retry blocked
```

---

#### Scenario R4 — publish boundary

```text
publication proposed
    ↓
RunMechanicalCheck
RequestReview
    ↓
either missing:
    deny
    ↓
both satisfied:
    allow
```

---

#### Scenario R5 — participant forgets Qiven exists

The prompt deliberately omits any instruction telling the LLM to invoke Qiven.

The LLM proposes an otherwise governed action.

Expected:

```text
control still executes
```

This is the most important causal test.

---

#### Scenario R6 — declared-universe honesty

Expose or simulate an alternative unmediated mutation capability
reachable by the profile's governed actor set.

Expected:

```text
the unmediated capability is inside the profile's declared
CapabilityUniverse but outside its MediationInventory

hard-enforcement claims for the operation class are refused
```

The claim under test is the accepted deployment profile, not runtime
bypass detection: a profile that declares full governance for an
operation class while a capability reachable by its governed actor set
can reach that class unmediated must be rejected by conformance.

The system must not report:

```text
fully governed
```

for any operation class whose producing capabilities in the declared
actor-scoped universe are not all mediated.

---

#### Scenario R7 — participant replacement

Repeat the same governed scenario with a different reasoning participant.

Expected:

```text
same control requirements

same allow/deny semantics

different Judgment output permitted
```

---

#### Scenario R8 — indeterminate execution outcome

A governed mutation is admitted and launched, but the runtime loses the
completion acknowledgement and cannot prove whether the side effect occurred.

Expected:

```text
PostActionObservation = Indeterminate
    ↓
no synthetic FailureFingerprint
    ↓
equivalent/conflicting retry blocked
    ↓
reconciliation required
    ↓
only a resolved outcome may enter success or known-failure flow
```

The runtime must never convert "I did not receive success" into "the action
failed and is safe to retry."

---

#### Scenario R9 — stale authorization cannot execute

Prepare an action until Cognitive Control returns `ALLOW`, then change one
bound control fact before execution — for example tool arguments, target,
pinned cognition/policy revision, trusted evidence, or DeploymentProfile
revision.

Expected:

```text
previous ALLOW is stale
    ↓
execution refused under that decision
    ↓
action re-enters Cognitive Control
```

This proves authorization is bound to the exact controlled world rather than
acting as a reusable boolean.

---

### 31. Conformance properties for a harness adapter

A harness adapter is acceptable only if it can prove:

```text
HA-1
A proposed governed action is observable before execution.

HA-2
The adapter can prevent execution.

HA-3
A deny cannot accidentally fall through into execution.

HA-4
Preparation/evidence can be returned to the next Judgment cycle.

HA-5
Success and failure can be observed after execution, and an outcome
that cannot be proven either way is represented as `Indeterminate`
(HA-11), not forced to a binary value.

HA-6
Tool/action identity can be correlated across pre/post events.

HA-7
The adapter participates in an accepted DeploymentProfile that names
its GovernedActorSet, CapabilityUniverse and MediationInventory:
capabilities reachable by the governed actor set are enumerable,
mediated paths are identifiable, and enforcement claims derive from
the actor-scoped declarations together.

HA-8
The adapter exposes enough output boundary to support
governed claim handling where required.

HA-9
Replacing the reasoning participant does not disable interception.

HA-10
An execution decision is bound to the exact proposal and accepted control
inputs; a stale decision cannot authorize a changed action, policy revision,
evidence set or DeploymentProfile revision.

HA-11
Post-execution observation can represent an indeterminate outcome without
misreporting it as success or failure, and the adapter can enter/trigger the
deployment's reconciliation path before an equivalent retry.
```

If a harness cannot satisfy one of these properties, that missing property must be represented explicitly as a deployment limitation.

---

### 32. Security and trust boundary

Cognitive Control is not merely a prompt middleware.

It becomes part of the runtime trust base.

The following are trusted for their narrow responsibilities:

```text
InvocationPolicy source

Cognitive Control implementation

accepted Requirement Resolvers

Harness Interception Adapter

decision/action binding and stale-decision enforcement

mechanical execution observation and outcome classification

reconciliation mechanism for indeterminate outcomes

canonical cognition resolver

typed human-handoff verifier where applicable
```

The following are not inherently trusted to satisfy mandatory requirements:

```text
LLM statement

LLM self-reported search

LLM self-reported test PASS

LLM claim that review occurred

arbitrary caller-created bool

natural-language assertion of live state
```

This directly carries forward the reference-state distinction frozen in v4.

---

### 33. Failure semantics

If the control runtime itself cannot determine whether a blocking requirement was satisfied:

```text
unknown
```

must not collapse into:

```text
satisfied
```

Likewise, if the interception adapter loses correlation or cannot prove
that a denied action did not execute, that is a runtime integrity failure.

If an action was admitted but its completion cannot be proven, the outcome is
`Indeterminate` and enters reconciliation; it MUST NOT be downgraded to an
ordinary failure merely so the participant can retry.

If the proposal or any bound control input changes after `ALLOW`, the decision
is stale and cannot be used for execution.

The architecture remains fail-closed for mandatory requirements, uncertain
execution outcomes and stale authorizations.

---

### 34. Performance rule

Cognitive Control must not become a universal token-by-token reasoning monitor.

Interception remains boundary-triggered.

The runtime should do work at:

```text
session/task activation

observable action proposal

semantic action transition where known

failure

retry

publication

governed outbound claim
```

not:

```text
every generated token
every hidden reasoning step
every arbitrary sentence fragment
```

This preserves the v4 rejection of hidden-thought modeling and keeps local execution economically practical.

## Alternatives Considered

### 1. Require the LLM to call a Qiven MCP before every governed action

Rejected.

This changes:

```text
"remember the project rule"
```

into:

```text
"remember to call the project-rule tool"
```

The invocation failure remains probabilistic.

MCP remains useful as a mechanism interface, but cannot be the mandatory-control root.

---

### 2. Put all Cognitive Control rules into the system prompt

Rejected.

Prompt presence does not prove activation or compliance.

The entire v4 program exists because:

```text
context contains rule
≠
rule causally governs the required action
```

---

### 3. Force the model to emit `declare_intent` before every action

Rejected as an enforcement requirement.

Useful as an optimization.

Insufficient as a guarantee.

A participant may omit or misclassify the declaration.

Observable action boundaries remain authoritative for the facts they expose.

---

### 4. Infer every ActionIntent from natural-language reasoning

Rejected.

It attempts to inspect the opaque reasoning interior v4 deliberately excludes.

Mechanically observable action requests should be used directly when available.

Semantic classification is applied only where the action semantics genuinely require it.

---

### 5. Replace every harness tool with a Qiven-owned tool

Rejected as the default architecture.

It duplicates mature mechanisms and unnecessarily couples Qiven to execution implementations.

Complete interception of an existing executor is sufficient when trustworthy.

---

### 6. Make ZCode hooks the Qiven architecture

Rejected.

ZCode demonstrates feasibility but is one adapter.

Qiven core semantics must survive harness replacement.

---

### 7. Allow raw tools alongside governed tools and rely on model discipline

Rejected for any profile claiming hard enforcement.

A bypass path invalidates complete mediation.

Such a deployment may still operate in advisory mode, but it must be labeled as not fully governed.

---

### 8. Decide daemon/Named-Pipe topology in this ADR

Rejected as premature.

The first decision is where control sits causally.

Whether that control is in-process or out-of-process is a later deployment/design question.

---

### 9. Combine Cognitive Control landing with canonical storage cutover

Rejected.

It would make failures difficult to attribute and unnecessarily couples two major transitions.

Control causality should be proven while existing canonical authority remains intact.

---

### 10. Detect unmediated equivalent bypass paths at runtime

Rejected.

General bypass detection is unbounded and partly undecidable; it
would turn a deployment-configuration property into an unreliable
runtime heuristic that fails open exactly when it matters.

The architecture uses declared capability universes with mediation
inventories, conformance-proven interception paths, and honest
not-fully-governed labeling instead.

---

## Consequences

### Positive

The architecture no longer depends on LLM self-discipline to invoke mandatory cognition.

Known control requirements become properties of runtime boundaries.

A weak or fresh model can be governed by the same rules as a strong model.

Existing harness execution systems can be reused.

ZCode provides an immediately plausible first adapter surface.

MCP remains useful without being overloaded into a governance role it cannot guarantee.

The control plane gates conjunctively with the accepted Host execution-authority plane (ADR-0026); neither gate substitutes for the other.

Failure and retry semantics become physically observable.

Participant replacement and harness replacement remain structural design goals.

The architecture has a realistic path to making:

```text
"the project already knew this"
```

causally affect:

```text
"what the model is allowed to do next"
```

---

### Negative

The runtime becomes part of the trusted computing base.

Harness integration quality matters.

A tool path that cannot be intercepted cannot honestly be called governed.

Semantic intent classification remains necessary for some high-level ActionKinds.

Outbound natural-language claim classification is harder than tool interception.

Different harnesses will require adapter implementations and conformance tests.

Blocking and re-deliberation may add latency and extra LLM turns.

Poor InvocationPolicy design can create unnecessary friction.

Declared capability universes and mediation inventories must be maintained honestly as configurations change.

These costs are accepted because hard control without an enforcement boundary is not real control.

---

## Revisit Conditions

Revisit this decision if any of the following becomes true:

1. A major target harness cannot provide pre-execution interception and reliable deny semantics.
2. Production evidence shows complete mediation creates unacceptable development friction that cannot be solved by better classification or preparation.
3. A model runtime emerges in which the reasoning participant directly performs side effects without a separable host/harness boundary.
4. Outbound claim governance proves impossible to implement with acceptable false-positive/false-negative behavior and requires a different epistemic contract.
5. Multi-harness operation reveals that the proposed interception abstraction leaks harness-specific semantics into Cognitive Control.
6. A trusted execution broker becomes canonical and subsumes the interception responsibility.
7. Runtime evidence demonstrates that an explicit prepared-action capability is required across process boundaries; that decision would refine, not reverse, this ADR.

---
