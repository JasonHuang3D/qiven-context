# Keep qiven-math a small deterministic external-semantics-free spatial vocabulary

## Context
Qiven needs reusable algebraic values across CAD, geometry, robotics, rendering boundaries, and later physics, but those domains carry different coordinate systems, tolerance policies, semantics, and performance representations.

## Decision
`qiven-math` owns small fixed-size algebraic values and operations only. It deliberately does not absorb geometry primitives, CAD entities, units, dynamic/decomposition-oriented linear algebra, product coordinate conventions, robotics policy, physics, or rendering API semantics.

The library is not intended to become a GLM/Eigen replacement or a general numerical framework. Broader domains remain separate layers such as geometry, units, linalg, CAD, robotics, physics, and rendering/scene boundaries.

## Alternatives Considered
Using one broad math library as the home for geometry, units, decomposition-heavy linear algebra, coordinate conversions, and rendering conventions; growing toward a general-purpose GLM/Eigen-style surface.

## Consequences
The core vocabulary stays deterministic and portable, while higher layers must explicitly own their semantic conversions and tolerance rules. Some functionality that is mathematically related remains outside qiven-math because semantic ownership matters more than convenience.

## Revisit Conditions
Revisit scope only when repeated downstream demand demonstrates an algebraic primitive is genuinely semantics-free, stable, and broadly shared.
