# Bounded process custody for every Qiven tool that spawns processes

## Context

The 2026-09-23 post-session incident (v19 aftermath) showed the v1 exec
design's survival property — "the child outlives the caller's shell" —
implemented WITHOUT a lifetime bound and cleaned up only by agent
discipline (`exec stop`): dozens of orphaned msbuild/cmd processes
(MSBuild node-reuse descendants plus abandoned runs, escaped from every
job via CREATE_BREAKAWAY_FROM_JOB) and a ghost raw-shell `find.exe`
held ~70% CPU past session end and IDE exit; an OS restart was
required. The owner directed a full architecture rebuild to production
grade (exec v2, devkit PR #27) and this ADR to codify the resulting law
after the fact.

## Decision

1. **Mechanical custody is the law.** Any Qiven-owned tool that spawns
   processes must bound the spawned tree's lifetime by OS enforcement,
   never by agent behavior. On Windows the sanctioned mechanism is a
   Job Object carrying `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (plus a
   process-count cap) held by a single named custodian (watchdog) that
   is itself a job member: custodian death — any cause — kills the
   tree instantly; a hard lease (`--max-lifetime`, default 3600 s,
   clamped [10, 86400]) bounds the tree even with a living custodian
   and no caller. An unstartable custody primitive means the child is
   not spawned (fail closed).
2. **Completion reaps.** A run/task completes when its primary
   completes; surviving tree members are terminated after a bounded
   output grace (1.5 s). Deliberate background survivors are not a
   supported semantic (no-daemon law); they are the leak class being
   eliminated.
3. **Tree completeness.** Custodied children never spawn with
   CREATE_BREAKAWAY_FROM_JOB; task children are created suspended,
   assigned to their job, then resumed (zero-race custody). Tool
   children that fan out worker nodes additionally run with
   `MSBUILDDISABLENODEREUSE=1` (defense in depth).
4. **The Qiven Operator's exec is the single sanctioned mechanism** for
   long/unknown-duration and survival-requiring execution; gate/run
   task children carry the same custody inline. A sweep piggybacked on
   every operator invocation terminates lease-expired runs and
   finalizes stale records (dead-man insurance without a daemon).
5. **Observability and honesty**: run records carry the custody
   identity (job name, custodian pid, lease deadline, live heartbeat);
   exit semantics preserve v1's contract (observed code; 124
   still-running at the supervision budget; `indeterminate` for
   unobserved exits) and add `expired` (killed by lease; business code
   never guessed).
6. **Standards**: the Devkit-canonical Python engineering standard
   (`docs/engineering/python-standard.md`) carries the spawn-law scar
   tissue as binding rules for all Python in the workspace; the
   design contract is `docs/design/exec-custody.md`.

## Alternatives Considered

1. **Patch v1 in place** (add taskkill sweeps, document the stop duty
   harder): rejected — the failure is architectural (survival without
   a bound, cleanup by agent behavior); the incident class had recurred
   across v18/v19 fixes (window discipline, no-detour law) without the
   leak surface shrinking.
2. **A central reaper service** (daemon scanning for orphans): rejected
   — violates the no-daemon law and adds a new always-on failure
   surface to cure a per-run defect; per-run custody plus the
   invocation-piggyback sweep covers the requirement without a service.
3. **Per-run deadline recorded but enforced only by callers**: rejected
   — behavioral enforcement is the class that just failed; the kernel
   must own the kill.
4. **POSIX-first portable custody**: deferred, not chosen — the
   governed platform is Windows; POSIX keeps watchdog-enforced leases
   with an honestly-recorded kernel-gap.

## Consequences

- A session can no longer leave invisible build processes burning CPU
  behind it: trees die at most one lease window after abandonment, and
  immediately when their custodian dies (including IDE job kills).
- The v1 "survival is best-effort and unbounded" semantics are
  superseded; survival remains (caller death does not kill a run) but
  is always lease-bounded.
- Rollout is progressive: devkit and qiven-context (shim pin) are
  covered; sibling repositories re-sync on their next touching batch
  (OBL-20260923T234500Z-B9C1D3).
- POSIX keeps watchdog-enforced leases and completion reaps but lacks
  the kernel kill-on-close guarantee; recorded as a platform gap, not
  silently claimed (design §3).

## Revisit Conditions

- A POSIX agent runtime joins the program with real exec usage →
  revisit POSIX kernel-grade custody (PDEATHSIG/subreaper) instead of
  the watchdog-alive-only guarantee.
- A legitimate requirement emerges for runs whose descendants must
  outlive the primary (supervisor patterns) → a new ADR must define
  their custody; the default remains completion-reap.
- A runaway-CPU class appears that the ACTIVE_PROCESS job cap does not
  cover → extend the job limits (CPU rate control) under this ADR.
- The manual-phase drift signal fires (engineering README protocol
  evolution question 5): uncustodied `subprocess` usage bypasses the
  custody layer in review → add the automated detector.
