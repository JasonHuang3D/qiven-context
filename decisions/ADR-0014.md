# Keep canonical vector values compact and scalar-aligned instead of encoding SIMD ABI

## Context
Canonical vector values cross many Qiven layers. Encoding platform SIMD width into those values would change layout, alignment, ABI expectations, serialization assumptions, and memory density for every consumer even when SIMD is not the relevant execution model.

## Decision
`VecN<T>` remains an aggregate, standard-layout, trivially-copyable canonical value with exactly `N * sizeof(T)` bytes and `alignof(T)`. There is no hidden padding, `alignas(16)` policy for `Vec3f`, union overlay, packed representation, or platform SIMD type in the canonical vectors.

Performance-specific layouts belong in batch APIs, structure-of-arrays representations, explicit SIMD kernels, or GPU kernels rather than being baked into the semantic value type.

## Alternatives Considered
Over-aligning `Vec3f` to 16 bytes for SIMD convenience; storing hidden fourth lanes; union overlays between scalar fields and SIMD registers; making canonical vector layout platform-dependent.

## Consequences
`Vec3f` remains 12 bytes and `Vec3d` remains 24 bytes. Canonical data stays dense and predictable. Explicit high-performance representations may require conversion or separate kernels, which is accepted to avoid contaminating the universal value vocabulary.

## Revisit Conditions
Revisit only if a future stable ABI or hardware execution requirement proves that the canonical representation itself, rather than a specialized compute representation, must change.

## Provenance
Genesis reconstruction from the committed representation policy and compile-time layout tests.
