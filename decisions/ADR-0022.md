# Treat cognition retrieval adequacy as a measured layered reliability property

## Context

During Qiven Operator dogfood, a Python-environment issue repeated a problem that qiven-context had already captured canonically in `MEM-20260913T170803Z-A61F2C` and implemented in `tools/resolve-python.cmd`. The relevant memory existed and remained active, but it was not retrieved before reasoning continued. The reasoning path then relied on older model-native conversation context and partially re-invented a weaker Python resolver.

This incident demonstrates two distinct failure modes:

1. a retrieval engine may exist but not be invoked at the point where a task changes materially;
2. a deterministic lexical/metadata retriever may pass closed-set acceptance while still lacking evidence that it provides adequate open-set recall for unanticipated tasks.

ADR-0003 deliberately kept canonical storage simple and made retrieval derived and replaceable. That decision remains sound. Its revisit condition explicitly says to reconsider retrieval when cold-boot acceptance or operational experience demonstrates insufficiency. This incident is such operational evidence.

Batch 004 cold-boot acceptance was a valuable safety test, but its rubric was a closed set of known assertions. Passing it established source discipline, anti-fabrication behavior, and recovery of the tested knowledge. It did not establish open-set retrieval adequacy for future task wording or semantic distance.

## Decision

Qiven keeps canonical cognition in auditable Markdown/YAML/JSONL/JSON Schema + Git. A database, vector index, embedding store, graph, or service remains derived and rebuildable rather than canonical.

Retrieval adequacy is now treated as a reliability property that must be measured rather than inferred from simplicity, intuition, or a single acceptance pass.

The qiven-context retrieval path must satisfy all of the following:

1. **Mandatory task-boundary retrieval.** Cold boot and every material task/domain transition must run a task-specific retrieval step before project-history facts are used. Retrieval may be automatic or explicitly invoked, but it must not depend on the reasoning model remembering that it should search.
2. **Layered candidate generation.** Structured selectors/IDs/scopes/obligations remain valuable, but retrieval must also evaluate lexical full-text and semantic retrieval as derived channels. Explicit relations/graph expansion may provide another channel. No single derived retriever becomes project authority.
3. **Semantic retrieval must be measured, not dismissed a priori.** A semantic/embedding candidate must be implemented or otherwise benchmarked against the deterministic baseline. The storage engine is not predetermined; SQLite FTS/BM25, an embedded vector index, a dedicated vector database, or another rebuildable mechanism are implementation choices to be selected from evidence.
4. **Fusion must preserve provenance.** When multiple retrieval channels are used, the result must preserve canonical source IDs/paths and selection reasons. Similarity scores never become truth or authority.
5. **Acceptance must include open-set recall.** The benchmark must contain held-out tasks whose wording is not copied from memory titles/tags, historical incidents expressed through paraphrase, task-switch scenarios, negative controls, and cross-domain distractors. Critical recall and acceptable retrieval noise must be defined before running the final benchmark so thresholds cannot be moved after results are known.
6. **Closed-set success is not evidence of open-set adequacy.** A test may only support the property it actually exercises. Future acceptance documents must state which retrieval property each test proves and which it does not.
7. **Complexity deferral must be falsifiable.** For foundational systems with silent false-negative failure modes, saying a deeper mechanism is "unnecessary" is insufficient. A deferral requires an explicit hypothesis, observable failure signal, frozen revisit trigger, and a credible path to compare the deferred alternative when the blast radius is high.

## Alternatives Considered

### Make a vector database canonical immediately
Rejected. The retrieval incident does not justify replacing auditable source truth with an opaque or service-dependent canonical store. ADR-0003's source/derived separation remains valuable.

### Patch BOOTSTRAP.md and keep retrieval architecture otherwise unchanged
Rejected. Mandatory invocation fixes one failure mode but does not answer whether deterministic retrieval has enough open-set recall.

### Wait for another retrieval failure before investing further
Rejected. The explicit ADR-0003 revisit condition has already fired. Requiring a second production-like miss would be another unmeasured gamble.

### Mandate one specific vector database now
Rejected. The current evidence requires semantic retrieval to be evaluated, not a specific product or deployment topology. Canonical data must remain independent of the chosen derived index.

## Consequences

qiven-context temporarily becomes the highest-priority Qiven engineering concern before Operator Phase 1 merge/release work resumes. The next work must establish a retrieval benchmark, mandatory invocation path, and measured comparison of deterministic, semantic, and hybrid retrieval.

This accepts additional implementation complexity because qiven-context is epistemic infrastructure: a retrieval false negative is often silent and can produce a plausible but historically wrong engineering decision. That failure mode deserves more redundancy than a subsystem whose errors fail loudly.

## Revisit Conditions

Revisit the exact retrieval stack after the benchmark provides evidence about recall, noise, latency, operational burden, rebuild cost, and provenance quality. Replace components freely if the canonical source and acceptance contract remain intact.
