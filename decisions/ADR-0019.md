# Make CAD a building-semantic pipeline behind provider boundaries rather than an arbitrary DWG interpreter

## Context
The CAD product goal is to transform architectural/floor-plan source data into a useful semantic 3D result. Treating every DWG as an arbitrary CAD universe would dramatically widen recognition, semantics, and validation scope without improving the initial building-domain objective.

## Decision
Use a provider abstraction for DWG/DXF and other source readers. Mature third-party parsing and geometry algorithms may be used behind that boundary, but Qiven owns the normalized CAD entity model, topology/semantic interpretation contracts, building model, and downstream transformation semantics.

The intended pipeline is:

DWG/DXF or other supported source -> normalized CAD entities -> 2D topology -> semantic building model -> parametric 3D -> mesh -> exchange/runtime targets such as glTF, USD, or UE-oriented integration.

The initial product is building-domain aware, not a promise to understand arbitrary unknown DWG semantics. Build a headless deterministic pipeline/CLI before an editor or DCC-style interactive shell so the semantic transformation can be tested independently from UI concerns.

## Alternatives Considered
Driving AutoCAD/3ds Max/UE as the primary architecture; interpreting arbitrary DWG content as the initial scope; building a UI/editor before a deterministic headless core; reimplementing mature file/geometry algorithms solely to own every low-level mechanism.

## Consequences
Input-provider technology can change without redefining Qiven's building semantics. DCC tools may remain optional adapters or validation aids rather than architectural centers. Scope remains bounded enough to test semantic accuracy and mesh/runtime behavior systematically.

## Revisit Conditions
Broaden beyond building-domain semantics only when a concrete product requirement justifies a new domain model and test corpus. Revisit provider choices independently from Qiven's normalized semantic contracts.
