# Trust GitHub account identity and remote state for current qiven-context governance

## Context

A stronger design could introduce independent hardware keys, signed governance envelopes, quorum, or biological-presence mechanisms. The project owner identified that such mechanisms do not solve the current project-governance threat model cleanly: an AI or attacker controlling the owner's devices and credentials can often cross the same practical boundary, while Qiven cannot independently prove biological identity.

Qiven nevertheless needs a deterministic current trust boundary for who governs canonical context and which repository state is authoritative.

## Decision

GitHub is the current identity/authentication trust provider for Qiven project governance, and GitHub remote state is the canonical published authority for qiven-context.

The root governance principal is GitHub account `JasonHuang3D`. The repository records semantic Qiven authorities separately from mere reasoning capability, but it accepts GitHub's account-level authentication result rather than attempting to prove that the biological person is physically operating the device.

The canonical qiven-context repository is `JasonHuang3D/qiven-context`, branch `main`. Local clones, filesystems, refs, cached SHAs, and device state are non-authoritative working copies. Current repository heads, visibility, workflow state, and CI must be resolved from GitHub when relevant instead of cached as canonical “live” state.

Possession of a clone is not governance authority. Git author name/email metadata is not authentication. Current account/device/GitHub compromise is an explicitly accepted residual risk rather than a problem Qiven pretends to solve.

This decision does **not** supersede ADR-0029. ADR-0029 is a narrower Host recovery fail-closed gate intended to prevent an ordinary transport sharing the owner token from clearing `Reconciling`/`Quarantined`; it is not a claim that Qiven can authenticate biological Jason for project governance.

Authentication architecture may be strengthened later only when real project requirements justify the added infrastructure.

## Alternatives Considered

Build a custom Qiven IAM now; require passwords; require a hardware-backed signing key for every governance action; attempt biometric/biological-human proof; treat local Git state or commit author email as identity.

## Consequences

The trust model is intentionally simple and explicit. Project continuity can move across machines while still anchoring published truth in one remote provider. The system is not designed to withstand compromise of the trusted GitHub account/provider at this stage.

Host recovery may retain stricter local-presence semantics when its narrower split-brain threat model independently justifies them.

## Revisit Conditions

Revisit when multiple independent governance principals exist, commercial/regulatory requirements demand stronger non-repudiation, supply-chain threat assumptions materially increase, or a project-owned signing/quorum system provides a justified security benefit.

## Provenance

Accepted directly by the project owner during the Qiven-v6 Context v2 governance design discussion.
