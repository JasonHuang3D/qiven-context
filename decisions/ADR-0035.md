# Bind participant roles to qualified model instances and client-tool capability classes through ContextView

## Context

The operating contract originally defined `jason-brother` and `jason-worker` as if
they were properties of one participant stack: jason-brother was effectively "the
ChatGPT cloud agent with connector access" and jason-worker was effectively "the
local ChatGPT Work agent". That fusion caused three problems:

1. **Semantic drift risk.** When a new participant combination appears (ZCode
   desktop + Jason, a future Claude Code session, a new OpenAI model), copying the
   ChatGPT workflow text verbatim re-derives roles from tool names instead of from
   responsibility, exactly the drift the owner rejected.
2. **Role confusion about the real axis.** The brother/worker distinction is
   fundamentally a model reasoning-capability distinction (deep semantic review,
   architecture and merge judgment versus bounded reliable execution loops), while
   the client tool (ChatGPT web, ChatGPT desktop/Codex, ZCode desktop, Claude Code)
   is a separate axis that determines the execution topology.
3. **Undisclosed model substitution.** Provider-side model routing can silently
   change the model serving a session (observed 2026-09-18: GLM-5.3 sessions
   repeatedly failed provider-side and work continued on GLM-5.3-Flash). Identity
   records must make such substitution visible, never silent.

## Decision

1. **Roles stay canonical and tool/model independent.** `jason-brother` and
   `jason-worker` are authority/responsibility packages defined in
   `collaboration/operating-contract.md`. ContextView material must not redefine
   them.
2. **Three orthogonal ContextView dimensions.**
   - **Role binding** — which qualified model instance currently fulfills a role
     for this view, declared as `binding_id = <role>-<family><version>[-<variant>]`
     (for example `jason-brother-glm5-3`, `jason-worker-glm5-3-flash`,
     `jason-brother-gpt6`, `jason-worker-gpt5-6sol`). Each binding records model
     family/version/variant/provider/reasoning tier, a `qualification` state
     (`untested | provisional | qualified`) with evidence, and is resolved
     `verify_live` per session.
   - **Client tool** — the concrete client/runtime (for example `chatgpt-web`,
     `chatgpt-desktop-codex`, `zcode-desktop`, `claudecode`) classified into a
     stable capability class (`cloud_terminal`, `cloud_desktop_hybrid`,
     `local_supervised_agent`, `host_mediated_agent`). Workflow profiles bind to
     capability classes, not to tool names; a new tool is classified, not
     hand-copied.
   - **Human preferences** — interaction preferences only
     (`views/humans/<human>.yaml`). Preferences adapt presentation and relay
     mechanics and never alter acceptance topology, authority, or governance.
3. **Qualification is evidence-based.** Naming a binding does not confer its
   role's authority. A binding is `untested` until it has executed at least one
   real task in the repository under the required gates, `provisional` when
   initial evidence exists but the standing review path has not yet run, and
   `qualified` when the evidence named in the view supports the role's standing
   authorities. Upgrade or downgrade of a qualification is a recorded context
   transaction.
4. **Live model resolution and disclosure duty.** A session must record which
   model actually served it when it materially differs from the declared binding.
   Work performed by a lower-tier or different model than the binding declares is
   still valid work, but the checkpoint must disclose the substitution and
   affected authority holders may require a replacement-tier review before
   merge-class actions.
5. **Initial GLM bindings for `ContextView<ZCode, Jason>`.** Deep semantic review,
   architecture, ADR drafting and merge-class judgment are bound to
   `jason-brother-glm5-3` (GLM-5.3 flagship); bounded local execution loops,
   builds, test gates and metered measurement work are bound to
   `jason-worker-glm5-3-flash` (GLM-5.3-Flash, MoE 18B-active, tuned for
   long-horizon agent execution). The rationale is the repository's own failure
   history: its costliest defects (K4 topology gap, canonical wording conflict,
   split-brain assumption) were semantic, so the flagship tier owns review, while
   execution workloads are deterministic and gate-protected, so the efficient
   tier owns them. Both bindings start `provisional`/`untested` respectively and
   follow rule 3.
6. **Branch naming.** Worker-disciplined local branches may use `zcode/<name>`;
   existing `jason-brother/<name>` and `jason-worker/<name>` prefixes remain
   valid. Git identity is never changed as workflow machinery.
7. **`chatgpt-jason` remains active and unchanged in semantics.** Its workflow
   document is reclassified as the `cloud_terminal`/`cloud_desktop_hybrid`
   instantiation of the same underlying contracts.

This decision refines the role separation of ADR-0004 and the ContextView model
of ADR-0030; it supersedes neither.

## Alternatives Considered

1. **Copy the ChatGPT view and rename the agent.** Rejected because it re-derives
   roles from tool names and reproduces exactly the semantic drift the owner
   rejected; workflow profiles must follow capability classes.
2. **Make ZCode a jason-brother instance by default.** Rejected because brother's
   merge-class authority is evidence-based; granting it by tool possession would
   contradict the governance principle that capability is not authority.
3. **Hard-code the GLM mapping without qualification states.** Rejected because
   provider-side routing can silently change the serving model (observed
   2026-09-18); without `verify_live` resolution and a disclosure duty the record
   would drift from reality.
4. **Extend the operating contract with a third role for desktop agents.**
   Rejected as unnecessary: the brother/worker pair already covers the
   responsibility split, and binding declares which model instance and tool
   fulfills them for a given view.

## Consequences

- `views/bindings/zcode-jason.yaml` and the capability-class workflow profile
  `views/workflows/supervised-agent.md` become the operating adaptation for
  ZCode + Jason; future participant combinations declare bindings instead of
  forking role definitions.
- Desktop tools with local execution can run higher-efficiency workflows (local
  batch -> push branch -> local `gh` PR -> owner review -> merge) provided the
  guardrails of `views/workflows/supervised-agent.md` and the handoff
  boundary of ADR-0036 are respected.
- Model substitution is now a recordable, reviewable event instead of an
  invisible one.
- The ADR-0032 agent-runtime validation exception continues to apply per its own
  scope; Windows-only tests may actually execute on JasonPC-resident runtimes
  instead of being skipped.

## Revisit Conditions

Revisit bindings when a new GLM generation, an OpenAI/Claude model change, or a
new client tool changes the capability map; requalification is a recorded context
transaction. Revisit the capability-class enumeration when a real participant
combination no longer fits any class, rather than pre-adding speculative classes.
Upgrade `jason-worker-glm5-3-flash` to `qualified` after its first authorized task
completes with gates green; upgrade `jason-brother-glm5-3` after the standing
review path has been exercised.

## Provenance

Accepted from the project owner's 2026-09-18 direction establishing the two-layer
architecture: canonical context independent of LLM, tool, and human; ContextView
carrying role-model bindings, client-tool classification, and human preferences.
The owner confirmed the brother/worker distinction is fundamentally a model
reasoning-capability distinction and directed that the GLM mapping be judged from
project evidence and written into context. Evidence: the 2026-09-18 remote cold
boot of `d81166b2b8b68eaaa17244c2ca450318b2cc2521` and the read-only design
session that preceded this transaction.
