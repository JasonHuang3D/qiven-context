# Prioritize Qiven DCR Windows transport before CAD and stage native transport behind supervisor acceptance

## Context

DCR is now the accepted bounded execution transport between Qiven Chat/Work and JasonPC. Its reliability directly affects interaction throughput for every later product line. The current official path still depends on a foreground Node/NPM process and console output, while recent acceptance work exposed environment-propagation, liveness-state, and UI/backend-decoupling failure modes. Large or continuous output must not be allowed to create unbounded memory/UI pressure in the transport process.

The prior product roadmap resumed at CAD after Foundation/Math/Context/Operator work. The project owner explicitly chose to insert a Windows DCR transport product before CAD because stabilizing the transport amortizes across all future Qiven work.

## Decision

Insert **Qiven DCR Windows** ahead of CAD in the active product roadmap.

Phase 0 / Batch 000 freezes the protocol and failure model before implementation.

V1 is a native Windows supervisor around the existing official `@wonderwhy-er/desktop-commander remote` implementation. It owns bounded logging, asynchronous pipe draining, exact process-tree lifecycle, health/liveness state, deterministic environment injection, graceful restart/stop, and a minimal Win32 UI. The console must cease to be a transport lifecycle dependency.

V2 may replace the supervised Node transport with a native WebSocket/session implementation only after protocol reconnaissance establishes a sufficiently understood, testable compatibility contract.

Do not preemptively add a general threading or networking subsystem to `qiven-foundation`. Runtime/network abstractions remain product-local until repeated real consumers demonstrate stable shared semantics. Extraction to a shared runtime/network layer or a small Foundation primitive is demand-driven and must continue to satisfy Foundation dependency, ownership, failure and cost laws.

The first transport milestone ends when bounded logging, lifecycle/reconnect behavior, exact-head validation transport, and memory/disk/UI bounds are tested and the client can operate without a human-managed scrollback-heavy console. At that point product priority returns to CAD.

## Alternatives Considered

Continue directly to CAD and tolerate the current foreground-console DCR path; patch only the current CMD launcher; immediately reimplement the full DCR wire protocol natively; build generic thread/network frameworks in Foundation before a concrete product consumer proves their semantics.

## Consequences

Near-term CAD work is intentionally delayed by one bounded transport milestone. In return, later product work gets a more reliable and lower-turn execution plane. V1 reduces protocol risk by supervising the known-good official client first. V2 remains available without making protocol reverse-engineering a prerequisite for the first reliability improvement.

Foundation remains small and downstream-demand-driven. Threading/networking needs discovered here become evidence for future shared layers rather than automatic Foundation scope.

## Revisit Conditions

Revisit if the official DCR protocol/client changes materially, if the supervisor cannot provide the required reliability boundary, if another product demonstrates a stable reusable runtime/network abstraction, or if the project owner reprioritizes CAD ahead of transport completion.

## Provenance

Accepted directly by the project owner in Qiven-v4 after DCR acceptance and the subsequent transport-stability architecture discussion.
