# Establish qiven-runtime as the shared native owner of process and execution-runtime semantics

## Context

Qiven DCR Windows Batch 001 requires exact child-process generation ownership, descendant containment, concurrent stdout/stderr drainage, bounded stop behavior, explicit process results, and later cancellation/timer/liveness facilities. These semantics are independent of Desktop Commander and are lower than product policy.

Keeping them inside `qiven-dcr-win` would make the DCR product own a generic runtime substrate and would require later products either to depend upward on DCR or to duplicate/extract the same machinery. ADR-0024 requires correct lower semantic ownership before polishing the product-local implementation.

Foundation is lower still and should remain focused on foundational vocabulary/primitives. Process supervision is too policy-rich to become Foundation merely because it uses operating-system primitives.

## Decision

Create `qiven-runtime` as a shared native layer above `qiven-foundation` and below native products.

The initial Runtime scope is intentionally narrow and demand-driven. Its first subsystem owns generic process-execution semantics required by DCR Batch 001:

- process-generation identity;
- child-process-tree ownership;
- explicit launch/wait/exit results;
- concurrent stdout/stderr byte drainage;
- bounded orderly and forced stop;
- deterministic cleanup of owned native resources;
- a Windows backend using `CreateProcessW`, Job Objects, pipes, and the minimum synchronization/threading needed by this contract.

Runtime does not own DCR-specific environment variables, authentication, relay health, retry/recycle policy, Supabase protocol, logging presentation, or Win32 UI.

The dependency direction is:

```text
OS / standard library
    -> qiven-foundation
    -> qiven-runtime
    -> qiven-dcr-win
```

Runtime consumes Foundation's types, contracts, checked arithmetic/conversions, and any accepted foundational native-resource primitive. If the placement audit finds a missing primitive that is intrinsically Foundation-level, add and validate that primitive in Foundation first rather than reimplementing it privately in every Runtime subsystem.

The first Runtime API should express portable process semantics where those semantics are already stable, while the only implemented backend in this batch may be Windows. Do not claim Linux/macOS support until continuously built and tested. Windows-specific implementation details stay behind the Runtime boundary rather than leaking into DCR product APIs.

## Repository boundary

`qiven-runtime` earns an independent repository because the semantic owner is now stable and its lifecycle differs from DCR product policy. This satisfies ADR-0018's stable-ownership criterion; multiple existing consumers are not required by ADR-0024.

The repository should use the Qiven Devkit managed engineering surface and resolve Foundation as an existing source dependency with an immutable CI integration pin. Runtime must not network-fetch Foundation during CMake configure.

## Migration of existing spike

The existing product-local `qiven-dcr-win::ProcessGeneration` implementation is an implementation spike/evidence source. Reuse tests, algorithms, and Win32 findings that survive review, but do not preserve its product namespace/API merely because code already exists.

The migration order is:

1. audit whether any primitive belongs in Foundation;
2. implement/validate required Foundation delta if any;
3. implement process-generation contract in `qiven-runtime`;
4. validate Runtime Debug/Release and its exact Foundation integration pin;
5. make `qiven-dcr-win` consume Runtime;
6. delete the duplicate generic product-local implementation;
7. continue DCR-specific Batch 001/002 work.

## Performance and resource law

Runtime process execution must be designed for long-lived high-output systems. It must not require retaining complete stdout/stderr histories, must drain both streams independently of UI/disk presentation, and must make allocation, buffering, thread ownership, blocking, and forced termination behavior explicit.

The generic Runtime layer exposes facts/mechanisms; product layers own presentation and higher-level retention/restart policy.

## Alternatives Considered

Keep ProcessGeneration inside DCR and extract later; place process supervision directly in Foundation; create a DCR-specific Windows helper library; wait for a second consumer before establishing Runtime.

## Consequences

DCR Batch 001 becomes a small cross-repository stack rather than one self-contained product repository. That coordination cost is accepted because it matches the semantic architecture and prevents product-local duplication from becoming the de facto lower layer.

Future native products may consume Runtime without depending on DCR. Runtime itself remains narrow; threading, timers, networking, schedulers, IPC, or plugin systems enter only when concrete lower-layer contracts require them.

## Revisit Conditions

Revisit if process semantics prove inseparable from product policy, if Runtime begins accumulating unrelated utilities without stable lower-layer ownership, or if a different shared-layer split provides materially clearer ownership/performance/lifecycle boundaries.

## Provenance

Accepted during Qiven-v4 after the project owner required AI-led development to place lower-level semantics correctly on the first serious implementation rather than imitate a human local-prototype/extract-later learning curve. The decision applies ADR-0024 to the concrete DCR process-supervision requirement and uses ADR-0018's stable-ownership criterion to justify the Runtime repository boundary.
