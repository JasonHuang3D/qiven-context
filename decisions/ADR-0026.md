# Enforce a host-side single-writer execution authority with leases and fencing before further mutating DCR use

## Context

Qiven previously treated accepted DCR as a bounded transport and relied on the active Chat/Work flow to select one coherent sequence of machine-local operations. During Qiven-v4 the project owner observed a catastrophic failure of that assumption: the ChatGPT UI produced two answer choices for one interaction and both choices executed concurrently against the same JasonPC DCR/MCP capability.

The exact internal product mechanism that created the duplicate response branches is outside Qiven's authority and is not inferred here. What matters architecturally is that a single conversational intent cannot be assumed to produce a single machine-local execution authority.

Current DCR history records tool calls but does not expose a stable caller/assistant-response identity capable of distinguishing two competing authority flows. Therefore post-incident logs cannot reliably attribute every local mutation to one response branch, and a procedural instruction such as "do not run two branches" cannot be a safety boundary.

Any concurrent authority can invalidate exact-head validation, clean-tree assumptions, fail-fast sequencing, repository ownership, and local state reasoning even when each branch is individually well behaved.

## Decision

Introduce a JasonPC-resident **Qiven Host Execution Broker** as the mandatory local authority boundary before mutating DCR execution resumes.

DCR becomes transport only. The broker, not Chat, Work, DCR, or a repository script, decides whether a local request is currently authorized to execute.

The first accepted broker must enforce a conservative global single-writer model across all Qiven local MCP operations, including reads. Read concurrency is intentionally not optimized until safe isolation semantics are proven, because a read racing a mutation can produce a false engineering decision even when the read itself is non-mutating.

Every assistant response or other remote execution flow that wants JasonPC access must begin a fresh execution transaction. A transaction receives:

- a unique execution identifier;
- an opaque lease identifier not reused across response turns;
- a monotonically increasing fencing epoch;
- a per-transaction monotonic request sequence;
- explicit scope/intent metadata suitable for bounded auditing without recording secrets.

All subsequent local operations require the active lease and current fencing epoch. A stale epoch is rejected even if a delayed caller later resumes.

## Split-brain behavior

The broker must not queue a second competing execution flow for later execution. If a second execution identity attempts to acquire or use JasonPC while another lease is active, the broker records the collision and enters a fail-closed **quarantined** state.

Quarantine means:

- no new local operation is admitted from either contender;
- a newly arriving competing request receives an explicit `CONCURRENT_EXECUTION_REJECTED`-class failure;
- already-started owned child work is observed to a safe atomic boundary rather than blindly killing arbitrary processes;
- the broker does not return automatically to ready merely because a timeout elapsed;
- owner/recovery reconciliation is required before execution authority is re-opened.

This intentionally sacrifices availability to preserve local state integrity.

## Broker state model

The minimum state machine is:

```text
ready
  -> leased
  -> ready                 normal explicit completion
  -> reconciling           disconnect / uncertain completion
  -> quarantined           competing authority or fencing violation

reconciling/quarantined
  -> ready                 only after explicit reconciliation/clear
```

Timeout or transport loss is not equivalent to lease release. A lost caller may have already launched an owned process, and a stale response may resume later. The broker must inspect its owned work and durable journal before authority can be reissued.

## Local enforcement

The broker is the only accepted Qiven path to local execution once this architecture is enabled. Direct Desktop Commander MCP access must not remain as an alternate mutating path around the broker.

The broker implementation must include:

- single broker-instance enforcement on JasonPC, using a Windows machine-local primitive such as an appropriately ACLed named mutex;
- exact child-process-tree ownership using Windows Job Objects for spawned processes;
- a local IPC endpoint with owner-scoped ACLs rather than an unauthenticated LAN listener;
- persistent monotonic fencing state that advances across broker restart so old leases cannot remain valid;
- sequence/idempotency checks that prevent replay of an already accepted request;
- append-only, bounded, rotated execution journaling;
- request/result digests and bounded metadata rather than secret values or unbounded stdout payloads;
- pre/post repository identity evidence when Git/repository operations are involved;
- deterministic rejection of requests that bypass the current lease.

The broker must not run as a broader-privilege Windows identity merely for convenience. The initial implementation should remain in the project owner's normal JasonPC execution context unless a later accepted architecture proves a narrower service identity is required.

## Transport integration

The long-term local call chain is:

```text
Chat / Work / future AI client
        -> remote transport (DCR or successor)
        -> Qiven Host Execution Broker
        -> qiven-runtime / filesystem / Git adapters
        -> Windows
```

The host broker is transport-independent authority infrastructure. DCR-specific connection, health, memory supervision, and UI remain DCR product concerns; generic process execution remains owned by `qiven-runtime` per ADR-0025.

## Immediate safety gate

Until a broker implementation has passed explicit split-brain acceptance, **mutating DCR execution on JasonPC is suspended**.

DCR may be used read-only for incident forensics when the requested operation itself cannot change local state. Remote GitHub-native qiven-context recording remains allowed because it does not mutate JasonPC. Machine-local mutation required to bootstrap the broker must use the project owner's explicit trusted local path rather than the unfenced DCR path.

Existing local worktrees touched before this decision must be treated as potentially contaminated until reconciled against Git/repository evidence. Do not reset, clean, commit, merge, or otherwise "repair" them merely to restore a visually clean state.

## Acceptance criteria

The broker is not accepted merely because it serializes two threads in a unit test. Acceptance must demonstrate on JasonPC that:

1. two independent execution clients cannot both obtain authority;
2. a second contender causes deterministic rejection and quarantine rather than delayed execution;
3. a stale lease/fencing epoch cannot execute after release, restart, or replacement;
4. concurrent requests under one lease obey strict sequence/idempotency rules;
5. direct local execution bypass is absent from the Qiven transport path used in production;
6. transport loss moves authority to reconciliation rather than silently freeing the host;
7. exact child ownership survives descendants and cleanup boundaries;
8. journal/recovery evidence is sufficient to determine what definitely completed without retaining secrets or unbounded output;
9. the broker itself remains single-instance and fail-closed across restart;
10. a synthetic two-response split-brain test proves at most one transaction can mutate JasonPC.

## Consequences

The execution transport becomes slightly more complex and intentionally less available during ambiguity. This is accepted because the prior assumption of a single conversational executor is no longer defensible.

The broker becomes the foundation for future AI-first local execution, not merely a patch for Desktop Commander. Other transports may later replace DCR without changing the JasonPC single-writer/fencing authority model.

## Revisit Conditions

Revisit global read serialization only after the broker can prove snapshot/isolation semantics for concurrent observation. Revisit the local IPC/service model if multiple legitimate local users or machines require controlled concurrent access. Do not remove fencing merely because the upstream Chat product later appears to stop generating concurrent response branches.

## Provenance

Accepted as a P0 architecture correction during Qiven-v4 after the project owner directly observed two ChatGPT answer choices concurrently driving the same DCR/MCP-connected JasonPC. Read-only incident forensics found no DCR caller identity suitable for reconstructing response-branch ownership, which makes host-side authority enforcement necessary even when upstream conversational behavior is normally single-flow.
