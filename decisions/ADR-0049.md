# Executable H1 kits, human-facing tooling, template-trust identity

## Context

The MVP-4 H1 kit (merged hours earlier as a prose document) instructed
the owner to hand-author workspace hook configuration and run inline
commands. The hook binary REQUIRED an assumed payload field the real
harness never sends; fail-closed then denied every tool call in the
owner's fresh session. The owner emergency-disabled all hooks and
directed the corrections this ADR codifies (engineering executed the
same turn; the ADR follows the emergency-authorization precedent of
ADR-0048).

## Decision

1. **H1 kits are executable packages, tool-built.** Every H1 acceptance
   point ships as a package produced by a repository tool under
   deploy-grade preconditions (clean tree, gate PASS receipt at the
   exact head): binaries, the COMPLETE ready configuration (no owner
   authoring), launchers, evidence collectors, rollback, and a
   GENERATED operation guide. Prose documents may only POINT at kits.
   The Devkit standard (`h1-kit.md`) is normative.
2. **UI review is the enable gate.** A session may write live-environment
   configuration files directly when the environment's own review
   (e.g. the ZCode hook-config review) must approve them before they
   take effect; the kit always carries the pre-change backup and a
   rollback script.
3. **Owner-facing content is executable content.** Commands are
   shell-labeled and shell-correct for the owner's actual shells; guides
   give exact UI actions and verbatim copy-paste payloads; owner-facing
   binaries obey the human-facing output law (staged boot output, every
   durable path named, heartbeat during healthy silence).
4. **Template-trust identity.** Identity that governs behavior comes
   from the trusted registration template; external-contract payload
   fields are corroborating evidence at most. An external field becomes
   REQUIRED only after a recorded real-world capture proves it (kits
   carry the capture step). This is the deny-118 root-cause law.

## Alternatives Considered

1. Keep prose kits with stricter checklists: rejected — the failure was
   structural (interpretation load on the owner, drift between doc and
   reality), not a checklist gap.
2. Make the extractor fail-open on missing fields: rejected — fail-closed
   is correct; the defect was the unverified REQUIRED assumption, not
   the closed failure.
3. Owner-configured session tokens via UI editing: rejected — the config
   the kit ships IS the artifact; the UI review approves, never authors.

## Consequences

- Every future H1 acceptance (MVP-7 dogfood, cross-user pipe test,
  Human Succession trials) consumes this law; existing prose kits are
  pointers or get rebuilt as packages on their next touch.
- The deny-118 class is closed at the design level (template identity +
  verify-then-require), not merely patched.

## Revisit Conditions

- A harness documents a stable payload identity field → the hook may
  adopt it as REQUIRED with a recorded capture, under this ADR.
- A kit consumer needs non-Windows launchers → extend the standard's
  layout per-platform without weakening the package law.
