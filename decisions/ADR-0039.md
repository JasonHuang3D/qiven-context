# Establish the three-plane C++ repository topology, re-home the process-execution layer as qiven-process, and confirm qiven-runtime as the Cognitive Control Runtime home

## Context

The owner directed a full-repository C++ architecture re-audit before
returning to the Runtime program: the early architecture (genesis batch,
2026-09-13) was deliberately paused by ADR-0018, and the project must
now confirm which repositories exist and which architectural layer each
represents, honoring the early agreements — cross-platform,
performance/stability first, runtime dynamic libraries on demand, and
headless-back-end-before-UI-front-end — without repeating the
quick-validation-then-refactor apprenticeship curve that
`software-engineering-philosophy.md` section 3 rejects.

The audit found the early architecture sound and remarkably complete:
ADR-0017 (layer by semantic responsibility), ADR-0009 (five separate
representation boundaries; no stable C++ ABI before 1.0; binary
boundaries only on concrete demand), ADR-0019 (headless deterministic
core before editor/DCC shells), ADR-0024 (downward semantic ownership).
One material conflict with current reality exists: ADR-0025 established
`qiven-runtime` as the process/execution-runtime layer for DCR, while
the same repository name was activated 2026-09-21 as the Cognitive
Control Runtime program home (ADR-0038 follow-on).

## Decision

### 1. Three-plane repository topology

Qiven C++ repositories occupy three planes. The planes are peers, not
layers of one stack.

**Plane A — native product stack** (ADR-0017 layer law):

```text
OS / standard library / deliberately selected mature third-party
    -> qiven-foundation            (low-level base; the CMake and
                                    header-visibility reference)
        -> qiven-math              (independent sibling; ADR-0013/14/15)
        -> [qiven-units]           (future; sibling, never under math)
        -> [qiven-process]         (future; renamed ADR-0025 layer)
        -> [qiven-networking]      (future)
        -> [qiven-geometry]        (future; consumes math + units)
        -> [qiven-scene / qiven-compute]  (future)
    -> product infrastructure      (qiven-dcr-win: Windows transport)
    -> product verticals           (CAD, robotics, physics; industrial
                                    gas stays stack-independent per
                                    ADR-0020)
    -> UI and workflow shells      (always after headless cores,
                                    ADR-0019)
```

**Plane B — cognition system** (project meta-infrastructure):
`qiven-context` (canonical truth) -> `qiven-context-draft` (frozen
executable specification) -> `qiven-runtime` (Cognitive Control
Runtime) with `qiven-host` (machine-local execution authority,
Windows-bound by design).

**Plane C — build and operations**: `qiven-devkit` (conventions,
templates, operator), `qiven-toolchain-win` (pinned tools).

Bracketed names are planning vocabulary under ADR-0018: a repository is
created only when a real consumer earns its coordination cost. Creation
triggers: `qiven-process` when DCR Batch 001 (or any product) resumes
process-execution work; `qiven-units`/`qiven-geometry` when the first
product with unit-bearing or geometric semantics begins; scene/compute/
networking on their first real consumers; product repos headless-first.

### 2. qiven-runtime name adjudication

`qiven-runtime` is the **Cognitive Control Runtime** home (ADR-0038
follow-on; Component ADL landed there 2026-09-21). The
process/execution-runtime layer defined by ADR-0025 — process
generations, child-tree ownership, concurrent drainage, bounded stop —
keeps its scope unchanged but is re-homed as the future
**`qiven-process`** repository above Foundation and beside math/units.
ADR-0025 is archived unchanged to `decisions/legacy/` (owner-directed
archival policy: ADRs are historical evidence; conflicting decisions
are superseded by new ADRs, never edited in place). The
`projects/runtime` domain model is rewritten for Cognitive Control and
the process layer's model moves to `projects/process` (status:
deferred).

ADR-0026's sentence assigning generic process execution to
"`qiven-runtime` per ADR-0025" now reads as assigning it to
`qiven-process`; no other ADR references the old meaning (audited
2026-09-21).

### 3. Representation and binary-boundary policy (reaffirmed)

ADR-0009 remains law and is reaffirmed with current external practice:
- default linkage is **static** libraries (performance, stability,
  build simplicity);
- runtime dynamic libraries / plugins are an **explicit, designed
  boundary** created only on concrete distribution/plugin demand
  (first likely consumer: CAD provider boundaries per ADR-0019), using
  a C ABI (`extern "C"`, opaque handles) — never native C++ layout,
  STL types, or exceptions across the boundary. Current industry
  consensus matches this shape (PIMPL/C-ABI plugin edges; Qt-style C++
  plugin ABIs are the documented counterexample);
- **C++20 modules are not adopted**: cross-compiler portability and the
  library ecosystem remain immature (2026 survey). Revisit when the
  three major compilers, CMake, and the dependency set converge.

### 4. Anti-apprenticeship gates (binding on all new layers)

1. **Architecture law before code**: a layer's architecture document
   (foundation.md / math.md pattern) is accepted before its first
   implementation; for the Runtime program this is the Component ADL
   Section 90 C++ type/interface design.
2. **First-implementation quality bar**: philosophy section 9 applies
   from the first non-disposable commit — ownership, lifetimes,
   recoverable failure channels, bounded resources, concurrency
   contracts, platform boundaries.
3. **Creation criteria**: ADR-0018 governs repository creation; no
   speculative layers.

## Alternatives Considered

Editing ADR-0025 in place (rejected: owner-directed archival policy;
ADRs are the project's reasoning history); keeping both meanings in one
`qiven-runtime` repository (rejected: couples the cognition program
with the DCR substrate, violating single-responsibility layering);
adopting C++20 modules now (rejected: ecosystem immaturity); promising
a broad stable C++ ABI or dynamic-lib default (rejected: ADR-0009
demand-gated boundary law).

## Consequences

The topology is authoritative for C++ direction: new repositories
follow the layer map and creation triggers; the Runtime program may
start C++ design immediately without name ambiguity; the paused DCR
process work has a named future home. Legacy archival becomes the
standard mechanism for conflicting ADRs (`decisions/legacy/`).

## Revisit Conditions

A plane-A layer's creation trigger fires (create the repository); a
concrete plugin/distribution demand appears (design the C-ABI boundary
per ADR-0009); the module ecosystem converges (revisit modules);
experience shows a plane boundary is wrong (new ADR, archiving this one
if materially conflicted).

## Provenance

Full-ADR audit 2026-09-21 (38 ADRs reviewed; one material conflict

archival mechanism the same day.
