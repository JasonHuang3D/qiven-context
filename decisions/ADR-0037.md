# Establish qiven-context-draft as the executable C++ specification of the cognition architecture

## Context

Natural-language architecture boundaries drift under maintenance, and any LLM
maintaining prose contracts inherits that drift. Pointers versus values, types
and call graphs state ownership, lifetime and causal order exactly, so
architecture rules can compile instead of erode. The owner and the acting agent
therefore produced `qiven-context-draft` (public repository, adopted into
qiven-devkit management): a compilable C++ specification of the cognition
architecture — `LLMCognition` as a pure value tree, an admission-gated
persistence service, a minimal store contract, and a runtime pointer graph —
together with runnable demonstrations of refused writes, restore ordering and
quarantined artifact restores.

## Decision

1. **C++ is the semantic bridge** for expressing, validating and redesigning the
   context cognition architecture. The human and the LLM reason through typed
   drafts; prose contracts remain the normative record until a typed form is
   formally accepted.
2. **`qiven-context-draft` is the design substrate** for the ContextKernel /
   context-engine line (roadmap order 2). Its candidate semantics — the pure
   value tree (R1), the lifetime/authority split (shared_ptr versus fencing
   epoch), admission-gated writes embedding the typed handoff boundary, the
   store contract with state-replication instead of event-sourcing, and
   participant changes as O(1) pointer rebinds — are design input to the kernel,
   not yet canonical mechanism.
3. **No capability cutover before validation.** Until the draft is formally
   validated, every current context capability stays authoritative: the prose
   contracts, the Operator, the bootstrap and transaction machinery, the K4/K5
   acceptance paths. The draft changes nothing about how qiven-context runs.
4. **The validation standard is an explicit obligation** (see
   `OBL-20260918T215000Z-B4D6A8`), not a claim. Validation must bind the draft's
   compiled semantics to the accepted contracts and name its delivery profile;
   passing code review alone does not validate a continuity mechanism.

This decision refines ADR-0033's representation-independent kernel direction
with a concrete executable vehicle; it supersedes nothing.

## Alternatives Considered

1. **Redesign in prose only.** Rejected: prose is the drift medium this
   architecture is demonstrably suffering from; the draft's compiled invariants
   (for example the value-tree member audit) catch mechanically what reviewers
   must otherwise remember.
2. **Replace context machinery as soon as the draft compiles.** Rejected:
   compilation proves syntax and the demo proves behavior of a toy store, not
   continuity. K4's lesson applies directly — a working mechanism is not an
   accepted mechanism.
3. **Rust or another language for the specification.** Rejected: the owner and
   the agent pair are fluent in C++, the Qiven native stack (Foundation, Math,
   Devkit conventions) is C++20, and the draft must read as native Qiven code.

## Consequences

- Canonical context now tracks the draft workstream through obligations and this
  ADR; the draft repository is registered in the repository inventory.
- Kernel and K5 design work must treat the draft's semantics as candidate input
  and reconcile conflicts against accepted contracts explicitly.
- The draft repo's own discipline (no serialization libraries, transport as
  sketch, MemoryStore proves the contract) is recorded in its README and AGENTS
  surface and is binding for work on that repository.

## Revisit Conditions

Revisit when the validation obligation completes (upgrade candidate semantics
into the kernel design), when the two-layer context/view boundary discussion is
decided (the draft already models participants as runtime parameters, not
cognition members), or when a store implementation beyond git becomes real.
