# Seal the Python ContextKernel reference implementation permanently

## Context

The Python ContextKernel (K1-K4: import/object model, transactions,
reads, archive, handoff; with compiler/R1/retrieval suites) served as
the representation-independent reference implementation of context
semantics. ADR-0037 established the `qiven-context-draft` executable
specification as its successor; ADR-0038's Runtime program consumes the
frozen v4 semantics there. On 2026-09-21 the same session that split
kernel suites out of the default gate (MEM-20260920T195644Z-B7E2F1)
then spent repeated debugging cycles extending the kernel's layout
model (legacy-decision subdirectories) — work with no production value
on a superseded surface. The owner directed a permanent seal.

## Decision

1. The Python ContextKernel is **sealed**: its test suites are removed
   from the suite registry (never registered, never run), its gates
   (`context-kernel`, `k4-handoff-acceptance`) and tasks
   (`full-tests`, `kernel-tests`, `merge-proof-kernel`,
   `k4-handoff-producer*`) are removed from the operator, and
   the package is museum-material under `legacy/tools/context_kernel/` (ADR-0041) and marks.
2. Sealed code is **not modified**: no debugging, extension, or
   optimization, including to support new canonical layouts. The
   legacy-decision archival layout (ADR-0039) therefore requires no
   kernel support. Unsealing requires a new accepted ADR.
3. Repo-contract validation continues through `context-local` /
   `context-docs` (repository-validator, record-lifecycle,
   cold-boot-contract, windows-python-resolution, references, diff,
   clean). Incidental imports of sealed modules by repo suites are
   tolerated read-only.
4. Consequences for adjacent records: ADR-0033 is superseded (the
   kernel object model's authority role is fully inherited by the
   frozen v4 specification + Runtime); MEM-20260920T195644Z-B7E2F1
   (gate-cost deferral) is closed — its subject no longer runs; the K5
   obligation (OBL-20260917T192300Z-A7C4E2) stays open but its target
   surface is the Runtime canonical-cognition delivery path
   (ADR-0038 §28), not the sealed kernel; the K4 handoff CONTRACT
   remains canonical text while its Python implementation is sealed —
   future Canonical Artifact Handoff trials require a Runtime-side
   implementation.

## Alternatives Considered

Continuing selective maintenance (rejected: the session's own evidence
— repeated debug cycles on legacy-layout support — is the cost being
rejected); deleting the code (rejected: sealed reference material and
history are preserved); unsealing per-change (rejected: reopening the
same cost sink).

## Consequences

Canonical transactions validate in ~45s (repo suites only) with no
kernel cost anywhere. Retrieval tools that import sealed modules keep
working read-only until the Runtime replaces them. No K4/K5 kernel
work exists anymore; acceptance evidence already recorded stays valid
history.

## Revisit Conditions

Only a concrete, owner-accepted need to run a kernel capability before
its Runtime equivalent exists (for example an artifact-handoff trial
requiring the sealed producer) — by a new ADR that names the exact
capability and duration.

## Provenance

Owner interruption during the 2026-09-21 ADR-0039 landing session,
after the legacy-layout kernel patch cycle (importer/reads iterations).
