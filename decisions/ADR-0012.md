# Preserve consumer edits with hash-tracked all-conflicts-first Devkit lifecycle operations

## Context
Devkit needs to update shared repository conventions without silently overwriting consumer edits, and brownfield repositories need an adoption path that does not assume Devkit already owns their files.

## Decision
Generation records Devkit ownership state and hashes. Sync preflights the union of old and new managed paths before applying changes; consumer modifications that cannot be reconciled with old/new template state become conflicts and abort the operation before normal mutation begins.

Brownfield adoption is a distinct check/apply lifecycle. It requires a clean Git-root repository with HEAD and no existing `.qiven` ownership state. Every managed path is classified as `EXACT`, `MISSING`, or `CONFLICT`. Any conflict aborts adoption. Successful apply preserves exact files, creates only missing managed files, then establishes Devkit metadata/state. Bootstrap-only and unrelated domain files remain untouched.

## Alternatives Considered
Blind overwrite from the latest template; metadata-only adoption that declares ownership over divergent files; making adoption and sync the same operation without an explicit ownership transition; requiring consumers to discard all local convention edits before updating.

## Consequences
Consumer edits are protected and lifecycle transitions remain explicit and reviewable. Devkit must maintain state schema/migration discipline and cannot assume its current template is semantically superior to every brownfield variant.

## Revisit Conditions
Revisit if richer three-way semantic merge becomes demonstrably safer than hash-based ownership or if repository scale makes current preflight mechanics insufficient.
