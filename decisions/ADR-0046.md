# Infrastructure layer model: toolchain -> devkit -> all repositories

## Context

The Devkit grew from a C++ repository template factory into the de-facto
owner of the operator runtime, engineering standards and conventions —
but its positioning stayed "C++ template manager": only C++-shaped
repositories could be adopted, engineering standards were vendored into
every repository and re-synced on every change (the ADR-0044 rewrite
cost one devkit PR plus four repository rolls for a text change), and
qiven-context — a heavy operator consumer — was left outside the
machinery entirely, hand-carryrying operator copies.

## Decision

1. **Layer model**: `qiven-toolchain-win` (pinned executables:
   cmake, clang-format; environment layer) is consumed by
   `qiven-devkit` (infrastructure tool package: operator runtime,
   gate/task machinery, formatter, conventions AND engineering
   standards as single canonical copies); **every** repository — C++,
   Python, tools — consumes the Devkit. The Devkit is tool-level
   infrastructure ("the workspace's IDE"), not a per-repository
   template vendor.

2. **Engineering standards are Devkit-canonical (D1, executed)**:
   `qiven-devkit/docs/engineering/` is the single canonical home of the
   implementation/testing/execution/specification standards;
   repositories carry only the AGENTS.md pointer (the agent-entry
   pattern, extended). Per-repository copies are retired; a standards
   change is one Devkit PR. The managed template set shrinks to
   executable machinery plus repository policy/config.

3. **Consumption moves from copies toward shim-plus-pin (D2)**: a
   consuming repository keeps a thin entry shim and a recorded Devkit
   pin instead of vendored machinery. Mechanism: the operator honors
   `QIVEN_TARGET_ROOT` (the shim points it at the consuming
   repository); shim resolution order is `QIVEN_DEVKIT_ROOT` env, then
   the workspace sibling layout, then explicit failure with
   instructions. qiven-context adopts this first: `tools/qiven.py` is
   the shim, the vendored operator copy (904 lines) is deleted,
   and `.qiven/operator.json` records `devkit_pin`.

4. **Path portability rule**: sibling-relative defaults are acceptable
   only as ONE resolvable strategy behind an environment override;
   tools must never REQUIRE the JasonWork layout. Existing hooks
   (`QIVEN_TOOLCHAIN_ROOT`, `QIVEN_DRAFT_ROOT`, `QIVEN_DEVKIT_ROOT`,
   `QIVEN_TARGET_ROOT`) are the pattern; the eventual unified
   workspace manifest (repo -> local path or remote ref) is future
   work inside this model.

5. **CMake/Python division (D4, deferred)**: sync/adopt/state/test
   logic (~1130 lines of CMake script mode) belongs in the Python
   operator layer; CMake keeps only build configuration. Deferred
   behind the RPA program by owner bandwidth, not by principle.

6. **Tool de-vendoring for the C++ repositories (D3, deferred)**:
   moving the remaining managed machinery copies to shim-plus-pin
   requires proving the isolated/CI consumption mode (bootstrap fetch
   of the Devkit at the pin); revisit after the RPA record layer
   lands.

## Alternatives Considered

Keep per-repository doc copies with managed sync (rejected: pure-text
churn at N+1 PRs per change with zero execution value); adopt context
into the C++ template family (rejected: wrong shape — the problem is
consumption, not templating); full immediate de-vendoring of all tools
(rejected: the single-repo-clone-runs-gates property is real value
until CI-mode bootstrap is proven); merging toolchain-win into devkit
(rejected: the executable-pin layer is clean and independent).

## Consequences

Standards changes are one PR. The operator has one maintained engine
per workspace instead of one copy per repository (context first).
Repository self-containment weakens from "carries its tools" to
"carries its pin" — accepted for context now, decided per-repository
later (D3). The draft's operator.json customization remains the
standing manual-patch exception until reconciled.

## Revisit Conditions

A repository needs gates in an environment without Devkit access and
no bootstrap path exists (re-vendor that repository); the workspace
manifest becomes necessary (multiple workspaces/sandboxes in routine
use); D3/D4 execution windows open after RPA milestones.

workspace resolver at the accepted endpoint. The revisit condition
above ("the workspace manifest becomes necessary") fired per
