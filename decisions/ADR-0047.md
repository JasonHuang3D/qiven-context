# Runtime Production MVP architecture (vertical slice, SQLite control journal, MVP-0..7)

## Context

The RCA proof program (RCA-0..RCA-16) is complete and the real-hook
experiment proved events reach the adapter, but the runtime remains at
"real traffic connected", not "production control loop closed": nothing
yet demonstrates that Runtime decides and enforces before a real side
effect, that authorized bytes are the executed bytes, that bypass paths
are denied, that control state survives restarts without blind retries,
or that one logical qiven-context mutation is atomic across records,
indexes, validation, and the Git ref. The RPA engineering proposal
(43c0535d section 8) awaited an owner decision on program acceptance
and batch order. On 2026-09-22 the owner supplied a Production MVP
Architecture document and directed its adoption as the implementation
baseline, its ADR/OBL landing, and immediate batch start.

## Decision

1. **One enforced vertical slice is the MVP.** Under the single initial
   DeploymentProfile `zcode-jason-context-record-mvp` (one Windows user,
   one qiven-context checkout, one foreground ZCode session, one
   RuntimeHost, one local commit as mutation-completion boundary), the
   only product scenario is: typed `qiven-record` request ->
   cognition activation -> intent classification -> requirement
   resolution -> decision binding -> execution admission -> exclusive
   mutation -> repository validation -> Git compare-and-swap commit ->
   outcome observation -> crash recovery, with any bypassing mutation
   of governed paths denied.

2. **Boundary of authority.** `qiven-record` is a typed request client
   and never edits qiven-context itself. RuntimeHost (session-resident,
   user-mode `qiven-runtime-host.exe`) is the sole mechanism executor
   and the production composition root; the ZCode hook is a thin
   fail-closed client. SQLite (pinned amalgamation, WAL/FULL) stores
   Runtime control facts and audit history only and MUST NOT become
   the domain source of truth; qiven-context files plus Git remain
   domain truth for the whole MVP.

3. **Delivery order MVP-0..MVP-7 replaces the RPA order.** The first
   ticket is MVP-0 (production contracts: ResourceScope and coverage
   claim, BeforeJudgment/ReDeliberate timing correction, ActivationReceipt
   and causal-parent semantics, versioned ResolverRegistry and complete
   EvidenceReceipt, complete CorrelationKey, 128-bit IDs and secure
   decision-token abstraction, state image marked test-only, profile/
   bundle/journal ports), then MVP-1 SQLite RuntimeJournal and recovery
   skeleton, MVP-2 cognition publisher and DeploymentProfile, MVP-3
   RuntimeHost/IPC/mechanical execution boundary, MVP-4 production ZCode
   hook adapter, MVP-5 typed records and Git candidate transaction,
   MVP-6 real ExecutionAuthority and end-to-end recovery, MVP-7 real
   dogfood and release gate. A batch completes only at its exit gate,
   not at merge. The RPA proposal's "file-backed RuntimeStateStore
   first" (RPA-1) is rejected in favor of the SQLite control journal
   from the start; its generalized `qiven-record`/local-domain-store
   first, persist-current-image, and CLI-direct-write tendencies are
   rejected for the reasons recorded in the architecture document
   section 2.

4. **The architecture document's normative content is binding for the
   MVP.** Its non-negotiable invariants (participant independence;
   immutable pinned generations; revision-identity vs content-identity
   separation; CAS-only commits; conjunctive cognition+execution
   authority; harness as observed boundary; no late-requirement
   backfill into the current Judgment; authorization binds final bytes;
   DispatchIntent durably recorded before external effect with
   Indeterminate-not-retry semantics; single writer plus fencing; no
   implicit dual-write; sealed kernel stays sealed; NotGoverned instead
   of overstated authority), its verification matrix, its 13 mandatory
   fault-injection points, and its Definition of Done govern the
   program. The document is homed in qiven-runtime
   docs/architecture/runtime-production-mvp-architecture.md by the
   MVP-0 batch; until then the owner-supplied original is the
   reference text.

5. **Publication boundary unchanged.** The MVP produces validated local
   commits only; no automated push, PR, or merge; a local commit is
   never presented as canonical publication. Post-MVP extensions
   (broader tools, multi-session, PR adapter, Snapshot-as-truth) are
   explicitly deferred and require their own decisions; the
   Snapshot-as-truth transition additionally requires its own ADR,
   migration gate, and rollback procedure.

6. **Governed-claim honesty.** A hard complete-mediation claim holds
   only for the mediated tuple (ZCodeForegroundSession,
   {FileSystemWrite, RecordMutation}, qiven-context governed paths);
   everything else returns NotGoverned. Before release, every
   write-capable ZCode tool entry point must be enumerated and proven
   mediated or disabled through real H1 tests.

## Alternatives Considered

RPA delivery order (generalized qiven-record and local domain store
first - rejected: second source of truth without proving control);
persisting the current state image (rejected: it cannot recover
dispatches, outcomes, leases, or correlations); CLI that both expresses
intent and writes files (rejected: bypasses RuntimeHost execution
authority); file persistence first with later strengthening (rejected:
real effects need transactions, uniqueness constraints, WAL durability,
recovery queries, and explicit crash points from the start); broad
record-type support early (rejected: control correctness before
superficial breadth).

## Consequences

qiven-runtime gains a concrete production path: from advisory
observation to provable production control for one explicit actor,
operation class, and resource scope. qiven-context keeps Git-backed
files as domain truth and gains a canonical machine-readable
invocation-policy instance (runtime/invocation-policy.yaml, MVP-2) as
the machine instance of the existing specification. The K5 goal
(OBL-20260920T235500Z-B6C1D8) stays sequenced behind the MVP: the
uncompressed delivery reference arrives with the MVP-2 bundle work.
ADR-0046 D3/D4 remain deferred behind this program. Baseline note: the
architecture document cites qiven-runtime 43c0535d; commits between
43c0535d and program start (d82a4920) are CI/registration/template
syncs only and do not affect the design baseline.

## Revisit Conditions

Real-use evidence from MVP-7 dogfooding triggers re-evaluation of the
deferred list (commit/publish as separate boundaries, broader tools and
repositories, multi-session actor isolation, richer resolvers, GitHub
publication adapter, record SDK); Snapshot-as-truth requires its own
ADR with migration, dual-read verification, old-writer shutdown,
cutover, rollback, and audit; two consecutive batches missing their
exit gates trigger architecture review rather than batch repetition
(constitution 17).
