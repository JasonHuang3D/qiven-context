# Permit jason-brother to merge validated batch branches after user-confirmed local validation

## Context
The prior workflow kept the user as the final merge operator by default even when jason-brother had direct GitHub write access. That preserved a clear authority boundary, but it also left the user performing repetitive merge commands after already executing the machine-local validation that jason-brother cannot run remotely.

## Decision
For Qiven batch work, jason-brother has standing authorization to merge the batch branch into `main` after all required gates for that batch are satisfied.

At minimum:

- the user must report the required local batch validation as passing;
- the tested branch head must be the exact head proposed for merge;
- jason-brother must perform exact remote review of the head/delta before merge;
- any required remote CI or other batch-specific gate must also be green;
- if the branch changes after the user's validated head, the changed head must be validated again before merge.

The merge must not use force-push or bypass required validation. A normal no-fast-forward batch merge is preferred when preserving the batch boundary is useful.

## Alternatives Considered
Keep every final merge as a manual user command; allow jason-brother to merge before local validation; treat a previously tested ancestor as sufficient after later branch changes.

## Consequences
The user keeps the machine-local validation role while repetitive final Git operations move to jason-brother. The exact-head rule prevents remote edits after testing from silently entering `main` without validation.

## Revisit Conditions
Revisit if the user revokes or narrows this authorization, or if future automation provides an equivalent auditable merge gate without requiring a conversational PASS report.

## Provenance
Accepted directly from the project owner during Context Phase 0 / Batch 002 closeout.
