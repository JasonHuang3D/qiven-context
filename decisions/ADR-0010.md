# Materialize Devkit conventions as independent repository snapshots

## Context
Qiven needs shared repository conventions without making every runtime repository depend on a live Devkit checkout or turning repository bootstrapping into a runtime dependency chain.

## Decision
qiven-devkit materializes ordinary files into generated or adopted repositories. Generated repositories contain their own scripts and engineering protocol and remain independently usable after generation. They do not call back into a Devkit checkout during normal repository use.

Responsibility stays separated: qiven-toolchain-win owns pinned executable build tools, qiven-devkit owns repository templates/conventions/lifecycle tooling, runtime repositories own their APIs and domain architecture, and a future qiven-workspace may own multi-repository composition.

## Alternatives Considered
Keeping generated repositories coupled to a Devkit checkout through symlinks, submodules, runtime wrappers, or mandatory callback scripts; using Devkit as ecosystem version composition.

## Consequences
Repositories stay self-contained and reviewable, while synchronization is an explicit operation rather than an ambient dependency. Shared conventions can drift intentionally and later be reconciled through Devkit lifecycle tooling.

## Revisit Conditions
Revisit if repository count or convention-update frequency makes explicit materialization operationally inferior to another model that preserves independence, auditability, and consumer ownership.
